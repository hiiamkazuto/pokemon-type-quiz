# コードベースアーキテクチャの改善

アーキテクチャ上の摩擦を浮き彫りにし、**モジュールを深くする機会**（浅いモジュール群を深いモジュールへと変えるリファクタリング）を提案します。その目的は、テスタビリティとAIによるナビゲーション性の向上です。

本コマンドはプロジェクトのドメインモデルを基礎とし、共有された設計語彙に基づいて構築されています：

- スキルツールを呼び出して `codebase-design` を実行し、アーキテクチャ語彙（**モジュール**、**インターフェース**、**深さ**、**シーム**、**アダプター**、**レバレッジ**、**局所性**）とその原則（削除テスト、「インターフェースこそがテスト面」、「1つのアダプターは仮説上のシーム、2つで真のシーム」）を把握してください。すべての提案においてこれらの用語を厳密に使用し、「コンポーネント」「サービス」「API」「境界」などの言葉への逸脱を避けてください。
- `GLOSSARY.md` に定義されたドメイン言語が適切なシームに名前を与えます。また、`docs/adr/` にあるADRは、本コマンドが蒸し返すべきではない過去の決定事項を記録しています。

## プロセス

### 1. 探索

**スキャン前のスコープ設定 — YAGNI原則。** モジュールを深くする作業は、将来の変更を容易にすることで投資を回収するため、最近変更が加えられたコードベースの領域に重点を置いてください。調査を始める前に、*どこ*を調査するかを決定します：

- ユーザーが特定の方向性（モジュール、サブシステム、課題点など）を指定した場合は、それに従い、以下の推論ステップをスキップしてください。
- 指定がない場合は、コミット履歴（`git log --oneline`）を十分に遡ってコードベースのホットスポット（頻繁に変更されているファイルや領域）を特定し、それらのパスを最優先で調査してください。変更が分散して明確なホットスポットが存在しない場合は、調査対象の網を広げてください。

まず、触れる領域に関連するプロジェクトのドメイン用語集（`GLOSSARY.md`）およびADRを読み込んでください。

次に、サブエージェントを起動してコードベースを探索させます。硬直的なヒューリスティクスに縛られず、有機的に探索を進め、摩擦を感じる箇所を記録してください：

- 1つの概念を理解するために、多数の小さなモジュール間を行き来する必要がある場所はどこか？
- インターフェースが実装とほぼ同じくらい複雑な**浅いモジュール**はどこにあるか？
- テスタビリティのためだけに純粋関数が抽出され、実際のバグがそれらの呼び出し方に潜んでいる場所（**局所性**の欠如）はどこか？
- 密結合したモジュールがシームを越えて漏れ出している場所はどこか？
- 現在のインターフェース経由ではテストされていない、あるいはテストが困難なコードベースの領域はどこか？

浅いと疑われるモジュールに対しては**削除テスト**を適用してください。それを削除した場合、複雑さは集約されるでしょうか、それとも単に別の場所へ移動するだけでしょうか？「集約される」という判定結果が、求めるシグナルです。

### 2. 候補をHTMLレポートとして提示

リポジトリ内にファイルを残さないよう、OSの一時ディレクトリに自己完結型のHTMLファイルを書き出します。一時ディレクトリは `$TMPDIR` から解決し、フォールバックとして `/tmp`（Windowsの場合は `%TEMP%`）を使用します。実行ごとに新しいファイルとなるよう `<tmpdir>/architecture-review-<timestamp>.html` に書き込んでください。完了後、ユーザーの環境に合わせてファイルを開き（Linux: `xdg-open <path>`、macOS: `open <path>`、Windows: `start <path>`）、絶対パスを伝えてください。

レポートのレイアウトとスタイリングには**Tailwind（CDN）**を使用し、グラフ、フロー、シーケンスなどの構造伝達には**Mermaid（CDN）**を使用します。Mermaidと手作りのCSS/SVGビジュアルを組み合わせます。関係性がグラフ形状の場合（コールグラフ、依存関係、シーケンス）はMermaidを使い、より表現力が必要な場合（ボリューム図、断面図、折りたたみアニメーション）は手作りのdivやSVGを使用してください。各候補には**ビフォー/アフターの視覚化**を含めます。視覚的にわかりやすく表現してください。

各候補について、以下のカードをレンダリングします：

- **ファイル** — 関連するファイルおよびモジュールの一覧
- **課題** — 現在のアーキテクチャが摩擦を引き起こしている理由
- **解決策** — 何を変更するかについての簡潔な説明
- **メリット** — 局所性とレバレッジの観点、およびテストがどのように改善されるかの説明
- **ビフォー/アフター図** — 横並びで独自に描画され、浅さと深いモジュールへの再構築を視覚化した図
- **推奨度** — バッジとしてレンダリングされる評価（`Strong`、`Worth exploring`、`Speculative` のいずれか）

レポートの最後には**最優先推奨**セクションを配置します。どの候補に最初に着手すべきか、およびその理由を記述してください。

**ドメインの表現には `GLOSSARY.md` の語彙を使用し、アーキテクチャの表現には `/codebase-design` の語彙を使用してください。** たとえば `GLOSSARY.md` で「注文（Order）」が定義されている場合は、「注文受付モジュール」と表現し、「FooBarHandler」や「注文サービス」とは呼ばないでください。

**ADRとの競合**: 提案候補が既存のADRと矛盾する場合、その摩擦がADRの再検討を正当化できるほど深刻である場合にのみ提示してください。カード内に明確に明記します（例: 「_ADR-0007と矛盾しますが、以下の理由から再検討の価値があります…_」という警告の強調表示）。ADRで禁止されている理論上のリファクタリングを無差別に列挙することは避けてください。

HTMLの完全な足場、ダイアグラムのパターン、スタイリングガイドラインについては [`HTML-REPORT.md`](HTML-REPORT.md) を参照してください。

この段階では具体的なインターフェースの提案は行わず、ファイルの書き出し後に「これらのうち、どれについて検討を進めますか？」とユーザーに確認してください。

### 3. ヒアリングループ

ユーザーが候補を1つ選択したら、スキルツールを呼び出して `grill` を実行し、制約、依存関係、深いモジュールの形状、シームの背後に配置される内容、維持すべきテストについて、決定ツリーに沿ってヒアリングを進めます。

決定事項が具体化するにつれて、ドメインモデルを最新に保つための副作用を同時に処理します。スキルツールを呼び出して `domain-language` を実行してください：

- **`GLOSSARY.md` にない概念に基づいて深いモジュールに命名する場合**: その用語を `GLOSSARY.md` に追加します。ファイルが存在しない場合は新規作成してください。
- **会話の中で曖昧な用語が明確になった場合**: その場で直ちに `GLOSSARY.md` を更新してください。
- **ユーザーが重要な根拠を持って提案候補を却下した場合**: 「_将来のアーキテクチャレビューで同じ再提案を行わないよう、この決定をADRとして記録しますか？_」と提案してください。将来の探索者が同じ提案を繰り返すのを防ぐために真に必要な場合にのみ提案し、一時的な理由（「今は手が回らない」など）や自明な理由でのADR作成はスキップしてください。
- **深いモジュールの代替インターフェース案を探索したい場合**: スキルツールを呼び出して `codebase-design` を実行し、その中の「2回設計する」並行サブエージェントパターンを使用してください。
