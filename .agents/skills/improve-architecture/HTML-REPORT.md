# HTMLレポート形式

アーキテクチャレビューは、OSの一時ディレクトリ内に自己完結型の単一HTMLファイルとして生成されます。TailwindとMermaidはどちらもCDNから読み込みます。Mermaidはグラフ形状の図を確実に描画し、手作りのdivやインラインSVGは断面図やボリューム図などの視覚表現を担当します。両者を適切に組み合わせてください。すべてをMermaidに依存すると単調な見た目になります。

## スキャフォールド（雛形）

```html
<!doctype html>
<html lang="ja">
  <head>
    <meta charset="utf-8" />
    <title>アーキテクチャレビュー — {{リポジトリ名}}</title>
    <script src="https://cdn.tailwindcss.com"></script>
    <script type="module">
      import mermaid from "https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs";
      mermaid.initialize({ startOnLoad: true, theme: "neutral", securityLevel: "loose" });
    </script>
    <style>
      /* Tailwindでカバーしづらい独自装飾のためのスタイル:
         シームの破線、手描き風の矢印など */
      .seam { stroke-dasharray: 4 4; }
      .leak { stroke: #dc2626; }
      .deep { background: linear-gradient(135deg, #0f172a, #1e293b); }
    </style>
  </head>
  <body class="bg-stone-50 text-slate-900 font-sans">
    <main class="max-w-5xl mx-auto px-6 py-12 space-y-12">
      <header>...</header>
      <section id="candidates" class="space-y-10">...</section>
      <section id="top-recommendation">...</section>
    </main>
  </body>
</html>
```

## ヘッダー

リポジトリ名、日付、およびコンパクトな凡例を配置します：実線ボックス = モジュール、破線 = シーム、赤矢印 = 漏れ出し、太い濃色ボックス = 深いモジュール。前置きの導入段落は省き、直ちに候補一覧へと進んでください。

## 候補カード

図が主役です。説明文は簡潔かつ平易にし、`/codebase-design` スキルの用語集にある語彙をそのまま自然に使用してください。

各候補は1つの `<article>` で構成します：

- **タイトル** — 簡潔にし、深いモジュールへの再構築内容を命名（例: 「注文受付パイプラインの集約」）。
- **バッジ行** — 推奨度（`Strong` = エメラルド、`Worth exploring` = アンバー、`Speculative` = スレート）、および依存関係の分類タグ（`in-process`、`local-substitutable`、`ports & adapters`、`mock`）。
- **ファイル** — 等幅フォントの一覧（`font-mono text-sm`）。
- **ビフォー/アフター図** — 最重要の要素。横並びの2カラム構成。後述のパターンを参照。
- **課題** — 1文で記述。何が問題を引き起こしているか。
- **解決策** — 1文で記述。何を変更するか。
- **メリット** — 箇条書きで各項目を簡潔に記述（例: 「テストが単一インターフェースに集中」「価格計算ロジックの漏洩防止」「浅いラッパーを4つ削除」）。
- **ADRコールアウト**（該当する場合） — アンバー色の枠内に1行で記述。

長々とした説明段落は配置しないでください。文章で説明しなければ伝わらない図であるなら、図自体を描き直してください。

## ダイアグラムパターン

候補の特性に合ったパターンを選択し、組み合わせます。すべての図を同じ見た目にせず、変化を持たせてください。

### Mermaidグラフ（依存関係や呼び出しフローの基本パターン）

「XがYを呼び、YがZを呼ぶという複雑な絡まり」を示す場合は、Mermaidの `flowchart` または `graph` を使用します。取って付けたような印象を与えないよう、Tailwindでスタイリングしたカードの中にラップしてください。`classDef` を使って漏れ出しの線を赤色、深いモジュールを濃色でスタイリングします。シーケンス図は「修正前: 6往復 → 修正後: 1往復」のような対比に適しています。

```html
<div class="rounded-lg border border-slate-200 bg-white p-4">
  <pre class="mermaid">
    flowchart LR
      A[OrderHandler] --> B[OrderValidator]
      B --> C[OrderRepo]
      C -.leak.-> D[PricingClient]
      classDef leak stroke:#dc2626,stroke-width:2px;
      class C,D leak
  </pre>
</div>
```

### 手作りのボックス＆矢印（Mermaidの自動レイアウトが馴染まない場合）

境界線とラベルを持つ `<div>` でモジュールを表現します。矢印には、relativeコンテナに対して絶対配置されたインラインSVGの `<line>` または `<path>` 要素を使用します。「修正後」の図で、グレーアウトされた内部構造を持つ太枠の深いモジュールを表現したい場合はこちらを採用してください（Mermaidでは適切な重厚感を出しにくいためです）。

### 断面図（階層化された浅いモジュールの表現に最適）

水平方向の帯（`h-12 border-l-4`）を積み重ねて、呼び出しが通過する階層を示します。修正前: 何も処理していない6枚の薄い階層。修正後: 責務が集約された1本の太い帯。

### ボリューム図（「インターフェースが実装と同じくらい広い」場合の表現に最適）

モジュールごとに2つの長方形を並べます。1つはインターフェースの公開表面積、もう1つは実装の規模を表します。修正前: インターフェースの長方形が実装の長方形とほぼ同じ高さ（浅い）。修正後: インターフェースの長方形が低く、実装の長方形が高い（深い）。

### コールグラフの集約

修正前: 入れ子のボックスとして描かれた関数呼び出しのツリー。修正後: 同じツリーが1つのボックスに集約され、内部化された呼び出しがボックス内で薄くフェード表示されている構成。

## スタイリング指針

- 企業向けダッシュボードではなく、洗練されたエディトリアル調のデザインを意識してください。余白を贅沢に取ります。見出しにはセリフ体の使用も適しています（`font-serif` はstone/slate系と調和します）。
- 配色は控えめにします。アクセントカラーを1色（エメラルドまたはインディゴ）選び、漏れ出しには赤、警告にはアンバーを使用します。
- 図の高さは約320pxに収め、スクロールせずにビフォー/アフターが快適に横並びで見えるようにします。
- 図の中のモジュールラベルには `text-xs uppercase tracking-wider` を使用してください。UIではなく設計図（概略図）として読めるようにします。
- スクリプトはTailwindのCDNとMermaidのESMインポートのみを使用してください。レポート自体は静的とし、Mermaid自体のレンダリング以外の余分なアプリケーションコードや対話機能は含めないでください。

## 最優先推奨セクション

少し大きめのカードを1つ配置します。候補名、選定理由を1文、および該当カードへのアンカーリンクを記載します。

## トーン

簡潔で平易な文章としつつ、アーキテクチャに関する名詞や動詞は `/codebase-design` スキルで定義された用語をそのまま使用してください。簡潔さを理由に用語の定義から逸脱してはいけません。

**厳密に使用すべき用語:** モジュール、インターフェース、実装、深さ、深い、浅い、シーム、アダプター、レバレッジ、局所性。

**代用を避けるべき表現:** コンポーネント、サービス、ユニット（モジュールの代用）／ API、シグネチャ（インターフェースの代用）／ 境界（シームの代用）／ レイヤー、ラッパー（モジュールの代用）。

**スタイルに合致する表現例:**

- 「注文受付モジュールが浅い — インターフェースが実装とほぼ一致している。」
- 「価格計算がシームを越えて漏れ出している。」
- 「モジュールを深くする: インターフェースを1つに集約し、テスト箇所を1箇所に限定する。」
- 「2つのアダプターがシームの存在を正当化している: 本番環境のHTTPとテスト用のインメモリ。」

**メリットの箇条書き**では、用語集の概念を使って効果を明示してください。「局所性: バグが1つのモジュールに集中」「レバレッジ: 1つのインターフェースでN箇所の呼び出し元に対応」「インターフェースが縮小し、実装がラッパー群を吸収」など。用語集にない「保守しやすい」「クリーンなコード」といった抽象的な表現は避けてください。

曖昧な表現や前置きを省き、要点に絞って記述してください。箇条書きにできる文は箇条書きにし、削れる箇条書きは削ってください。`/codebase-design` の用語集にない単語を新造する前に、用語集にある単語を活用してください。
