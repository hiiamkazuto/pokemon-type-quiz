# テスト駆動開発

TDDとは、レッドからグリーンへのループです。本スキルは、そのループを通じて残す価値のあるテストを生み出すためのリファレンスです。良いテストとは何か、テストはどこに配置すべきか、アンチパターン、およびループのルールを定めています。すべてのセクションが毎サイクル適用されます。ループの後ではなく、ループの前および最中に参照してください。

コードベースを探索する際は、テスト名やインターフェースの語彙がプロジェクトのドメイン言語と一致するよう、`GLOSSARY.md`（存在する場合）を読み込み、触れる領域に関連するADRを尊重してください。

## 良いテストとは何か

テストは実装の詳細ではなく、公開インターフェースを通じて振る舞いを検証します。コードは全面的に変更される可能性がありますが、テストは変更されるべきではありません。良いテストは仕様書のように読め（「有効なカートでユーザーがチェックアウトできる」という名前からどのような機能が存在するかが明確にわかります）、内部構造に依存しないためリファクタリングを生き延びます。

具体例については [tests.md](tests.md) を、モックの指針については [mocking.md](mocking.md) を参照してください。

## シーム — テストを配置する境界

**シーム**とは、テストを行う対象となる公開された境界のことです。内部に手を伸ばすことなく外部から振る舞いを観察できるインターフェースを指します。テストはシームに対して配置し、内部実装に対して配置してはいけません。

**事前に合意したシームでのみテストを作成してください。** テストを書く前に、テスト対象とするシームを書き出し、ユーザーに確認を取ります。確認されていないシームに対してテストを書いてはいけません。すべてのものを網羅してテストすることはできません。事前にシームを合意しておくことで、あらゆるエッジケースではなく、クリティカルパスや複雑なロジックに対してテストの労力を確実に注ぐことができます。

「公開インターフェースは何であり、どのシームをテストすべきか？」と確認してください。

そのインターフェースの構造自体に疑問がある場合（モジュールの深さ、シームを置くべき位置、インターフェースが何を公開すべきかなど）は、「codebase-design」を指定してスキルツールを呼び出し、用語の定義を確認してください。これはモジュール、インターフェース、深さ、シーム、アダプター、レバレッジ、局所性に関する共有の知識源であり、セッションとして実行するものではなく参照用のリファレンスです。

## アンチパターン

- **実装との過度な結合** — 内部の協力オブジェクトをモック化する、プライベートメソッドをテストする、または裏口（インターフェースを使わずに直接データベースにクエリするなど）で検証すること。兆候：リファクタリングを行った際、外部の振る舞いは変わっていないのにテストが壊れる。
- **トートロジー** — アサーションにおいて、コードの計算方法をそのまま再計算してしまうこと（`expect(add(a, b)).toBe(a + b)`、同様の手法で手動作成したスナップショット、定数をそれ自身と等しいと検証するなど）。構造上必ず合格してしまい、コードのバグを検知できません。期待値は、独立した信頼できる情報源（既知の正しいリテラル値、手計算による具体例、仕様書など）から取得する必要があります。
- **水平スライス** — すべてのテストを先に書き、その後にすべての実装を書くこと。一括作成されたテストは想像上の振る舞いを検証してしまいます。ユーザーから見た振る舞いではなく構造をテストすることになり、現実の変更に対して鈍感になる上、実装を理解する前にテスト構造に縛られてしまいます。代わりに**垂直スライス**で作業を進めてください — 1つのテスト → 1つの実装 → 繰り返し。各テストを、前回のサイクルで学んだことに応答する**曳光弾**として進めます。

## ループのルール

- **グリーンの前にレッド。** まず失敗するテストを書き、それをパスする最小限のコードだけを書きます。将来のテストを先回りして予測したり、推測に基づく機能を追加したりしてはいけません。
- **一度に1つのスライス。** 1サイクルにつき、1つのシーム、1つのテスト、1つの最小限の実装を進めます。
- **リファクタリングはループ内で行わない。** リファクタリングはレッドからグリーンへの実装サイクルではなく、レビュー段階（`code-review` スキルを参照）に属します。
