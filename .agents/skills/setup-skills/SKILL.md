# スキル環境のセットアップ

各エンジニアリングスキルが前提とするリポジトリごとの設定を初期構築します：

- **Issueトラッカー** — Issueの管理場所（デフォルトはGitHub。ローカルのマークダウンファイルも標準でサポート）
- **トリアージラベル** — 5つの標準的なトリアージ役割に使用する文字列
- **ドメインドキュメント** — `GLOSSARY.md` やADRの配置場所、およびそれらを読み込む際の利用ルール

これはプロンプト駆動のスキルであり、決定論的なスクリプトではありません。現状を調査し、判明した内容を提示し、ユーザーに確認を取った上で書き込みを行ってください。

## プロセス

### 1. 調査

現在のリポジトリを調査して初期状態を把握します。決めつけず、存在しているものを確認してください：

- `git remote -v` と `.git/config` — GitHubのリポジトリか？どのリポジトリか？
- リポジトリ直下の `AGENTS.md` と `CLAUDE.md` — どちらかが存在するか？すでに `## Agent skills` セクションが含まれているか？
- リポジトリ直下の `GLOSSARY.md` と `GLOSSARY-MAP.md`
- `docs/adr/` および任意の `src/*/docs/adr/` ディレクトリ
- `docs/agents/` — このスキルの過去の出力がすでに存在しているか？
- `.scratch/` — ローカルのマークダウンによるIssueトラッカーの規約がすでに使用されている兆候
- `triage` スキルがインストールされているか？（このスキルと同じ階層にある `triage` スキルフォルダ、または利用可能なスキル一覧内の `triage`）。これによってセクションBを実行するかどうかが決まります。
- モノレポの兆候 — `pnpm-workspace.yaml`、`package.json` 内の `workspaces` フィールド、または独自の `src/` を持つ `packages/*` の存在。これらは真に大規模なマルチパッケージリポジトリにのみ存在します。存在しない場合は、ほぼすべてのリポジトリと同様に単一コンテキストとなります。

### 2. 調査結果の提示と確認

存在するものと不足しているものを要約します。その後、各セクションを順番に進めます（1セクション提示し、1つ回答を得てから次へ進む）。

ユーザーが一言で承諾できるように、各セクションの先頭には推奨の回答を提示してください。選択肢が真に分岐する場合のみ1行の説明を添えてください。調査によってすでに確定しているセクションは完全にスキップします（`triage` が未インストールの場合はセクションB、モノレポでない場合はセクションCをスキップ）。

**セクションA — Issueトラッカー**

> 説明：Issueトラッカーとは、このリポジトリの課題や要望を管理する場所です。`to-tickets`、`triage`、`to-spec` などのスキルがここから読み込み、ここへ書き込みを行います。`gh issue create` を呼び出すべきか、`.scratch/` の下にマークダウンファイルを書き込むべきか、あるいは指定された他のワークフローに従うべきかを判断する必要があります。このリポジトリで実際に作業を追跡している場所を選択してください。

基本方針：これらのスキルはGitHub向けに設計されています。`git remote` がGitHubを指している場合はGitHubを提案してください。それ以外の場合（またはユーザーが希望する場合）は以下を提示します：

- **GitHub** — リポジトリのGitHub IssuesでIssueを管理（`gh` コマンドを使用）
- **ローカルマークダウン** — このリポジトリ内の `.scratch/<feature>/` 配下のファイルとしてIssueを管理（個人プロジェクトやリモートのないリポジトリに適しています）
- **その他**（Jira、Linearなど） — ワークフローを1段落で説明するようユーザーに求めます。スキルはその内容を自由形式の文章として記録します。

選択結果を `docs/agents/issue-tracker.md` に記録します。GitHubのテンプレートには「外部PRをリクエスト対象とする」フラグがあり、デフォルトで**無効**になっています。この設定は無効のままにし、質問として取り上げないでください。外部からのPRをトリアージキューに含めたいユーザーは、後からファイル内のフラグを切り替えることができます。

**セクションB — トリアージラベルの体系** `triage` スキルがインストールされていない場合は、このセクションを完全にスキップしてください（調査で判明済み）。インストールされていないスキルにラベルは不要です。

インストールされている場合は、質問を1つだけ行ってください：

> デフォルトのトリアージラベルをそのまま使用しますか？（推奨: **はい**）

デフォルトは5つの標準的な役割であり、各ラベルの文字列はその名前と同じです（`needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix`）。「**はい**」の場合はそのまま書き込みます。ユーザーが「いいえ」と答えた場合（通常は既存のトラッカーで別の名前、例えば `needs-triage` の代わりに `bug:triage` などを使用している場合）にのみ、重複作成を防ぎ既存のラベルを適用できるよう上書き設定を収集してください。

**セクションC — ドメインドキュメント** デフォルトは**単一コンテキスト**です（リポジトリ直下に1つの `GLOSSARY.md` と `docs/adr/` を配置）。これはほぼすべてのリポジトリに適合するため、質問せずに書き込んでください。

調査でモノレポの兆候が見つかった場合にのみ、**マルチコンテキスト**（ルートの `GLOSSARY-MAP.md` からコンテキストごとの `GLOSSARY.md` ファイルを参照する構成）を提示してください。その上でどちらの構成を希望するか確認してください。

### 3. 確認と編集

以下のドラフトをユーザーに提示してください：

- `CLAUDE.md` または `AGENTS.md` のいずれか編集対象のファイルに追加する `## Agent skills` ブロック（選択ルールはステップ4を参照）
- `docs/agents/issue-tracker.md`, `docs/agents/domain.md`, および `docs/agents/triage-labels.md`（最後のファイルは `triage` がインストールされている場合のみ）の内容

書き込みを行う前にユーザーに編集の機会を与えてください。

### 4. 書き込み

**編集するファイルの選択：**

- `CLAUDE.md` が存在する場合は、それを編集します。
- 存在せず `AGENTS.md` が存在する場合は、それを編集します。
- どちらも存在しない場合は、どちらを作成するかユーザーに質問してください（勝手に決めないでください）。

`CLAUDE.md` がすでに存在するときに `AGENTS.md` を作成してはいけません（逆も同様です）。常にすでに存在している方を編集してください。

選択したファイルにすでに `## Agent skills` ブロックが存在する場合は、重複して追記するのではなく、その内容を直接更新してください。周囲のセクションに対するユーザーの編集内容を上書きしてはいけません。

追加・更新するブロック：

```markdown
## Agent skills

### Issue tracker

[Issueの管理場所に関する1行の要約]。詳細は `docs/agents/issue-tracker.md` を参照。

### Triage labels

[ラベル体系に関する1行の要約]。詳細は `docs/agents/triage-labels.md` を参照。

### Domain docs

[構成に関する1行の要約 —「単一コンテキスト」または「マルチコンテキスト」]。詳細は `docs/agents/domain.md` を参照。
```

`### Triage labels` のサブブロックを含め、`docs/agents/triage-labels.md` を書き込むのは、`triage` がインストールされておりセクションBを実行した場合のみです。そうでない場合は両方とも省略します。

次に、このスキルフォルダ内にあるテンプレートをベースとしてドキュメントファイルを書き込みます：

- [issue-tracker-github.md](./issue-tracker-github.md) — GitHub Issueトラッカー
- [issue-tracker-local.md](./issue-tracker-local.md) — ローカルマークダウンのIssueトラッカー
- [triage-labels.md](./triage-labels.md) — ラベルマッピング（`triage` がインストールされている場合のみ）
- [domain.md](./domain.md) — ドメインドキュメントの利用ルールと構成

「その他」のIssueトラッカーの場合は、ユーザーの説明をもとに `docs/agents/issue-tracker.md` を一から作成してください。

### 5. 完了

セットアップが完了したこと、および今後はどのエンジニアリングスキルがこれらのファイルを読み込むかをユーザーに伝えてください。後から `docs/agents/*.md` を直接編集できる旨も伝えてください（このスキルを再実行する必要があるのは、Issueトラッカーを変更する場合や一からやり直す場合のみです）。
