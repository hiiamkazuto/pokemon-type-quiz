# コードベース設計

**深いモジュール**を設計します。小さなインターフェースの背後に多くの振る舞いを隠蔽し、クリーンなシームに配置し、そのインターフェース経由でテスト可能にします。コードを新規設計または再構築する際は、常にこの用語体系と原則に従ってください。その目的は、呼び出し元へのレバレッジ、保守者への局所性、そして全員へのテスタビリティの提供です。

## 用語集

これらの用語を厳密に使用してください。「コンポーネント」「サービス」「API」「境界」などの言葉で代用せず、一貫した用語体系を保つことが本スキルの目的です。

**モジュール** — インターフェースと実装を持つあらゆる構成要素。規模は問いません（関数、クラス、パッケージ、全レイヤーを貫く垂直スライスなど）。*推奨しない表現*: ユニット、コンポーネント、サービス。

**インターフェース** — 呼び出し元がモジュールを正しく利用するために把握すべきすべての情報。型シグネチャだけでなく、不変条件、順序制約、エラーモード、必要な設定、パフォーマンス特性も含みます。*推奨しない表現*: API、シグネチャ（型レベルの表面情報のみを指すため狭すぎます）。

**実装** — モジュールの内部にあるコード群。**アダプター**とは区別されます。モジュールは「実装が大きく小さなアダプター（Postgresリポジトリなど）」にも、「実装が小さく大きなアダプター（インメモリのフェイクなど）」にもなり得ます。シームが話題の中心である場合は「アダプター」を、それ以外の場合は「実装」を使用してください。

**深さ** — インターフェースにおけるレバレッジ。呼び出し元（またはテスト）が学習すべきインターフェース単位あたりに実行できる振る舞いの量。小さなインターフェースの背後に膨大な振る舞いを備えているモジュールを**深いモジュール**、インターフェースが実装とほぼ同等に複雑なモジュールを**浅いモジュール**と呼びます。

**シーム（接合部）**（マイケル・フェザーズ） — その場所のコードを直接編集することなく振る舞いを変更できる場所。モジュールのインターフェースが存在する*位置*です。シームをどこに置くかは、背後に何を配置するかとは独立した独自の設計判断です。*推奨しない表現*: 境界（DDDの境界づけられたコンテキストと混同されやすいため）。

**アダプター** — シームにおいてインターフェースを満たす具体的な実装。内部の実態ではなく、果たす*役割*（どのスロットを埋めるか）を表します。

**レバレッジ** — 呼び出し元が深さから享受する恩恵。学習するインターフェース単位あたりの機能の多さを指します。1つの実装が、N箇所の呼び出し元とM個のテストにわたって投資を回収します。

**局所性** — 保守者が深さから享受する恩恵。変更、バグ、知識、検証が呼び出し元全体に拡散せず、1箇所に集中することを指します。1箇所の修正で全体が修正されます。

## 深いモジュール vs 浅いモジュール

**深いモジュール** = 小さなインターフェース + 充実した実装:

```
┌─────────────────────┐
│ 小さなインターフェース │  ← 少数のメソッド、シンプルな引数
├─────────────────────┤
│                     │
│      深い実装       │  ← 複雑なロジックを隠蔽
│                     │
└─────────────────────┘
```

**浅いモジュール** = 巨大なインターフェース + わずかな実装（これを避ける）:

```
┌─────────────────────────────────┐
│       巨大なインターフェース     │  ← 多数のメソッド、複雑な引数
├─────────────────────────────────┤
│            薄い実装             │  ← 単に素通りするだけ
└─────────────────────────────────┘
```

インターフェースを設計する際は、以下を検討してください：

- メソッドの数を減らせるか？
- パラメータをシンプルにできるか？
- より多くの複雑さを内部に隠蔽できるか？

## 原則

- **深さは実装ではなくインターフェースの性質です。** 深いモジュールは、内部的に小さくモック可能で交換可能な部品群で構成できます。それらは単にインターフェースの一部ではないだけです。モジュールはインターフェースにある**外部シーム**だけでなく、自身のテストでのみ使用される実装内部の非公開な**内部シーム**も保持できます。
- **削除テスト。** そのモジュールを削除した状態を想像してください。複雑さが完全に消滅する場合、それは単なるパススルー（素通り）です。複雑さがN箇所の呼び出し元に分散して再燃する場合、そのモジュールは存在価値を果たしています。
- **インターフェースこそがテスト面です。** 呼び出し元とテストは同じシームを通過します。インターフェースを飛び越えて内部をテストしたくなった場合、モジュールの形状を見直してください。
- **1つのアダプターは仮説上のシーム、2つのアダプターで真のシーム。** シームを挟んで実際に変化するものがある場合にのみシームを導入してください。単一のアダプターしか存在しないシームは単なる不要な間接層です。

## テスタビリティのための設計

優れたインターフェースはテストを自然なものにします：

1. **依存関係は内部生成せず、外部から受け取る。**

   ```typescript
   // テスト容易
   function processOrder(order, paymentGateway) {}

   // テスト困難
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **副作用を起こさず、結果の値を返す。**

   ```typescript
   // テスト容易
   function calculateDiscount(cart): Discount {}

   // テスト困難
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **公開表面積を小さく保つ。** メソッド数が少なければ必要なテスト数も減ります。引数が少なければテストのセットアップもシンプルになります。

## 概念の関係性

- **モジュール**はちょうど1つの**インターフェース**（呼び出し元とテストに提示する公開面）を持ちます。
- **深さ**はモジュールの性質であり、その**インターフェース**に照らし合わせて測定されます。
- **シーム**は、モジュールの**インターフェース**が存在する場所です。
- **アダプター**は**シーム**に位置し、**インターフェース**を満たします。
- **深さ**は、呼び出し元に**レバレッジ**を、保守者に**局所性**をもたらします。

## 採用しない定義・表現

- **「インターフェース行数に対する実装行数の比率」としての深さ**（アウスターハウト）: 実装の行数を水増しすることを助長してしまいます。本スキルでは代わりに「レバレッジとしての深さ」を採用します。
- **TypeScriptの `interface` キーワードやクラスの公開メソッドに限定した「インターフェース」**: 狭すぎます。ここでのインターフェースには、呼び出し元が把握すべきすべての知識を含めます。
- **「境界」**: DDDの「境界づけられたコンテキスト」と混同しやすいため使用を避けます。**シーム**または**インターフェース**と表現してください。
