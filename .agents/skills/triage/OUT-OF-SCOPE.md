# スコープ外ナレッジベース

リポジトリ内の `.out-of-scope/` ディレクトリは、却下された機能リクエストの永続的な記録を保存する場所です。2つの目的があります：

1. **組織の記憶** — 機能が却下された理由を残し、Issueがクローズされてもその判断理由が失われないようにする
2. **重複の排除** — 過去に却下された内容と合致する新しいIssueが届いた際に、議論を蒸し返すことなく前回の決定事項を提示できるようにする

## ディレクトリ構造

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

Issueごとではなく、**概念**ごとに1ファイルを作成します。同じ内容を要求する複数のIssueは1つのファイルにまとめられます。

## ファイル形式

データベースのエントリというよりも、短い設計文書のように、読みやすく落ち着いた文体で記述してください。段落、コード例、具体例を用いて、初めて読む人にも理由が明確で役立つようにします。

```markdown
# Dark Mode

このプロジェクトではダークモードやユーザー向けテーマ設定をサポートしません。

## スコープ外である理由

レンダリングパイプラインは `ThemeConfig` で定義された単一のカラーパレットを前提としています。
複数のテーマをサポートするには以下の対応が必要になります：

- コンポーネントツリー全体を包むテーマコンテキストプロバイダー
- コンポーネントごとのテーマ対応スタイル解決処理
- ユーザーのテーマ設定を保持する永続化層

これは大幅なアーキテクチャの変更であり、コンテンツ作成にフォーカスするというプロジェクトの方針と一致しません。
テーマ設定は、出力を埋め込んだり再配布したりする下流の利用側で対応すべき関心事です。

```ts
// 現在のThemeConfigインターフェースは実行時の切り替えを想定していません：
interface ThemeConfig {
  colors: ColorPalette; // 単一パレット、ビルド時に確定
  fonts: FontStack;
}
```

## 過去のリクエスト

- #42 — 「ダークモード対応の追加」
- #87 — 「アクセシビリティ向上のためのナイトテーマ」
- #134 — 「ダークテーマの選択機能」
```

### ファイルの命名

概念を表す簡潔でわかりやすいケバブケースの名前を使用してください（`dark-mode.md`、`plugin-system.md`、`graphql-api.md`）。ファイルを開かなくても、ディレクトリを閲覧しただけで何を却下したかが把握できる名称にします。

### 理由の記述

「欲しくないから」ではなく、なぜ不要なのかという実質的な理由を記述してください。適切な理由の例：

- プロジェクトのスコープや設計思想（「本プロジェクトはXに注力しており、テーマ設定は下流側の関心事です」）
- 技術的な制約（「これをサポートするにはYが必要になりますが、本プロジェクトのZアーキテクチャと衝突します」）
- 戦略的な判断（「〜という理由から、BではなくAを採用することを選択しました」）

理由は長期にわたって有効なものにしてください。「今は忙しすぎる」といった一時的な事情を理由にするのは避けてください。それは却下ではなく単なる延期です。

## `.out-of-scope/` を確認するタイミング

トリアージ中（ステップ1：状況の把握）に、`.out-of-scope/` 配下のすべてのファイルを読み込みます。新しいIssueを評価する際は：

- リクエストが既存のスコープ外概念と一致するか確認します
- キーワードではなく概念の類似性で判定します（「ナイトテーマ」は `dark-mode.md` に一致します）
- 一致が見つかった場合はメンテナーに提示します：「これは `.out-of-scope/dark-mode.md` と類似しています。[理由] により過去に却下されましたが、今も方針に変更はありませんか？」

メンテナーの対応：

- **確認（方針維持）** — 新しいIssueが既存ファイルの「過去のリクエスト」リストに追加され、その後クローズされます
- **再検討** — スコープ外ファイルが削除または更新され、Issueは通常のトリアージ工程に進みます
- **不一致** — 関連はあるものの別物であると判断し、通常のトリアージ工程に進みます

## `.out-of-scope/` に書き込むタイミング

バグではなく**改善要望**が `wontfix` として*却下*された場合のみ書き込みます。これはIssueと同様に改善要望のPRにも適用されます。同じリクエストが新しいコードとして再度持ち込まれないよう、却下されたPRもここに記録します。

すでに**実装済み**であるために `wontfix` としてクローズする場合は、ここには**書き込まないでください**。それは実装済みの機能であり、却下された機能ではありません。ここに記録してしまうと、誤った却下情報として重複チェックを汚染することになります。実装済みの場合は、その機能がすでにどこに存在するかをクローズ時のコメントで案内します。

作業の流れ：

1. メンテナーが機能リクエストをスコープ外と判断する
2. 一致する `.out-of-scope/` ファイルがすでに存在するか確認する
3. 存在する場合：新しいIssueを「過去のリクエスト」リストに追記する
4. 存在しない場合：概念名、決定内容、理由、最初の過去リクエストを記載した新しいファイルを作成する
5. 決定内容を説明し、`.out-of-scope/` ファイルに言及したコメントをIssueに投稿する
6. `wontfix` ラベルを付与してIssueをクローズする

## スコープ外ファイルの更新または削除

過去に却下された概念についてメンテナーが方針を変更した場合：

- 該当の `.out-of-scope/` ファイルを削除します
- スキル側で古いIssueを再オープンする必要はありません（それらは過去の記録です）
- 再検討のきっかけとなった新しいIssueは、通常のトリアージ工程に沿って進めます
