# トリアージ

プロジェクトのIssueトラッカー上のIssueを、トリアージ役割で構成されたシンプルな状態遷移に沿って進行させます。

このリポジトリが外部のプルリクエストをリクエスト対象として扱っている場合（Issueトラッカー設定を参照）、トリアージはそれらも対象とします。**PRとはコードが添付されたIssue**であり、役割、状態、状態遷移はすべて共通で、後述の「PR向け」と記された差分のみが異なります。プレーンな `#42` という指定は、トラッカー設定に従ってIssueまたはPRとして解決してください。

トリアージ中にIssueトラッカーへ投稿するすべてのコメントやIssueには、必ず以下の免責事項を冒頭に含める**必要があります**：

```
> *This was generated by AI during triage.*
```

## 役割

2つの**カテゴリ**役割：

- `bug` — 何かが破損・故障している
- `enhancement` — 新機能または改善

5つの**状態**役割：

- `needs-triage` — メンテナーによる評価が必要
- `needs-info` — 報告者からの追加情報を待機中
- `ready-for-agent` — 仕様が確定し、自動エージェントが着手可能
- `ready-for-human` — 人間による実装が必要
- `wontfix` — 対応しない

PRの場合、添付されたコードに照らし合わせて同じ状態を解釈します。`ready-for-agent` は指示書が添付されエージェントが差分に対して次のステップを進める状態を意味し、`ready-for-human` は人間がマージ可能な状態を意味します。

トリアージされたすべてのIssueには、カテゴリ役割と状態役割がそれぞれちょうど1つずつ付与される必要があります。状態役割の間で競合が発生した場合は、他の操作を行う前にメンテナーに警告して確認してください。

これらは標準の役割名であり、Issueトラッカーで実際に使用されるラベル文字列とは異なる場合があります。そのマッピング情報はすでに提供されているはずです。提供されていない場合は、ユーザーに `/setup-skills` を実行するよう促してください。

状態遷移：ラベルのないIssueは通常、最初に `needs-triage` となります。そこから `needs-info`、`ready-for-agent`、`ready-for-human`、または `wontfix` に遷移します。`needs-info` は報告者が返答した時点で `needs-triage` に戻ります。メンテナーはいつでも手動で上書きできます。不自然に見える遷移には注意を促し、進める前に確認を取ってください。

## 呼び出し方

メンテナーは `/triage` を実行し、希望する作業を自然言語で伝えます。その要求を解釈して対応してください。例：

- 「対応が必要なものを確認したい」
- 「#42 を見てみよう」
- 「#42 を ready-for-agent に移動して」
- 「エージェントが着手できるものは何がある？」

## 対応が必要な項目の表示

Issueトラッカーに問い合わせを行い、古い順に3つのグループに分けて提示します：

1. **ラベルなし** — トリアージ未実施。
2. **`needs-triage`** — 評価が進行中。
3. **前回のトリアージ記録以降に報告者の動きがあった `needs-info`** — 再評価が必要。

PRが対象に含まれる場合は、これらのグループに外部PRも含め、各行に `[PR]` または `[Issue]` というタグを付けてください。一覧に表示するのは*外部の*PRのみです（誰を外部とみなすかはトラッカー設定で定義されます）。共同開発者の進行中のPRはトリアージの対象外です。この除外ルールは一覧表示時のみ適用され、明示的に指定されたPRは作成者に関わらず常にトリアージされます。

件数と各項目の1行要約を表示し、メンテナーに選択させてください。

## 特定のIssueまたはPRのトリアージ

1. **状況の把握** IssueまたはPRの全容を読み込みます（本文、コメント、ラベル、作成者、日付。PRの場合は差分も含む）。過去のトリアージ記録を解析し、解決済みの質問を再度尋ねないようにします。プロジェクトのドメイン用語集を活用し、該当領域のADRを尊重しながらコードベースを探索します。コードベースに対して2つの確認を実行してください。(a) **重複の確認** — 要求された文言だけでなくドメインの概念から要求された動作が既存実装にないか検索し、どこを確認したか報告します。すでに存在する場合は、実装済みとしての `wontfix` となります（ステップ5）。(b) **過去の却下履歴の確認** — `.out-of-scope/*.md` を読み込み、今回の要求と類似するものがないか提示します。

2. **提案** 理由を添えてカテゴリと状態の推奨をメンテナーに伝えます。併せて、要求に関連するコードベースの簡潔な要約（すでに実装されているかどうかを含む）を提示します。メンテナーからの指示を待ちます。

3. **主張の検証** 質問攻めを行う前に、報告内容が正しいか検証します。バグの場合は、報告者の手順に沿って再現を試みます。PRの場合は、差分が説明通りの動作をするか確認します（ブランチをチェックアウトし、関連するテストやコマンドを実行します）。結果を報告してください：確認済み（コードパス付き）、再現失敗、または情報不足（`needs-info` とすべき強い兆候）。検証が確認できていると、はるかに堅牢なエージェント向け指示書が作成できます。

4. **質問攻めによる具体化（必要に応じて）** 要求をさらに詰める必要がある場合は、スキルツールを2回呼び出し、「grill」と「domain-language」を実行します。1ラウンドずつ質問を重ねて内容を具体化し、決定が下されるごとにドメイン用語を洗練させ、`GLOSSARY.md` やADRをその場で更新します。

5. **結果の適用:**
   - `ready-for-agent` — エージェント向け指示書のコメントを投稿します（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — エージェント向け指示書と同様の構造ですが、なぜ委譲できないのかの理由を明記します（人間の判断が必要、外部アクセス権が必要、設計上の決定事項、手動テストなど）。
   - `needs-info` — トリアージ記録を投稿します（後述のテンプレート参照）。
   - `wontfix` — *理由*に応じたコメントを添えてクローズします：
     - **実装済み** — 該当の変更がコードベースにすでに存在しています。該当箇所の場所を示してください。`.out-of-scope/` には**書き込まないでください**（このナレッジベースは*却下された*要求のためのものであり、実装済みの機能のためのものではありません）。
     - **却下（バグ）** — 丁寧な説明を記載した上でクローズします。
     - **却下（改善要望）** — `.out-of-scope/` に記録し、コメントからそこへリンクを貼った上でクローズします（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 役割を適用します。部分的な進捗がある場合は任意でコメントを添えます。

## 状態の直接指定

メンテナーが「#42 を ready-for-agent に移動して」と指示した場合は、その判断を信頼して役割を直接適用してください。これから実行する内容（役割の変更、コメント、クローズ）を確認してから実行します。質問攻めの工程はスキップします。質問攻めを経ずに `ready-for-agent` へ移行する場合は、エージェント向け指示書を作成するかどうか確認してください。

## needs-info のテンプレート

```markdown
## Triage Notes

**What we've established so far:**

- 決定事項1
- 決定事項2

**What we still need from you (@reporter):**

- 質問事項1
- 質問事項2
```

質問攻めの過程で解決した内容はすべて「これまでに確定した事項」に記録し、作業内容が失われないようにしてください。質問内容は「詳細を教えてください」といった曖昧なものではなく、具体的で行動可能なものにしてください。

## 前回のセッションの再開

IssueまたはPRに過去のトリアージ記録が存在する場合は、それらを読み込み、未解決の質問に報告者が回答しているか確認し、更新された状況を提示してから作業を再開してください。解決済みの質問を再度尋ねてはいけません。
