# エージェント向け指示書の作成

エージェント向け指示書とは、IssueやPRが `ready-for-agent` に移行した際に投稿される構造化されたコメントです。これは自動エージェントが作業の基準とする正式な仕様書となります。元の本文やディスカッションは背景情報であり、エージェント向け指示書こそが契約書です。

指示書には**エージェントが何をすべきか**を記載します。これはIssueとPRの両方に適用されます。Issueの場合はゼロから変更を構築することを意味し、PRの場合は*既存の差分に対して*残されている作業（仕上げ、不足箇所の補完、レビュー指摘事項への対応）を意味します。どちらの場合も原則は同じです。後述のPRの例でその違いを示します。

## 原則

### 詳細さよりも永続性を重視する

Issueは何日も、あるいは何週間も `ready-for-agent` の状態に留まることがあります。その間にコードベースは変化します。ファイルの名前変更、移動、リファクタリングが行われても有用であり続けるように指示書を記述してください。

- **推奨**: インターフェース、型、振る舞いの規約を記述する
- **推奨**: エージェントが探索または変更すべき特定の型、関数のシグネチャ、設定の構造を指定する
- **非推奨**: ファイルパスを参照する（古くなって陳腐化するため）
- **非推奨**: 行番号を参照する
- **非推奨**: 現在の実装構造がそのまま維持されると決めつける

### 手順ではなく振る舞いを記述する

システムが**何を**すべきかを記述し、**どのように**実装すべきかは記述しないでください。エージェントはコードベースを新たに探索し、独自に実装方針を決定します。

- **良い例:** 「`SkillConfig` 型は、`CronExpression` 型の省略可能な `schedule` フィールドを受け付ける必要がある」
- **悪い例:** 「src/types/skill.ts を開き、42行目に schedule フィールドを追加する」
- **良い例:** 「ユーザーが引数なしで `/triage` を実行したとき、対応が必要なIssueの要約を表示する必要がある」
- **悪い例:** 「メインのハンドラー関数内に switch 文を追加する」

### 完全な受け入れ条件

エージェントは作業がいつ完了したかを把握できる必要があります。すべてのエージェント向け指示書には、具体的でテスト可能な受け入れ条件が必須です。各条件は個別に検証可能でなければなりません。

- **良い例:** 「`gh issue list --label needs-triage` を実行すると、初期分類を通過したIssueが返される」
- **悪い例:** 「トリアージが正しく動作すること」

### スコープ境界の明示

対象外とする事項を明記してください。これにより、エージェントが過剰な作り込みを行ったり、隣接する機能について勝手な推測をしたりすることを防ぎます。

## テンプレート

```markdown
## Agent Brief

**Category:** bug / enhancement
**Summary:** 何を行う必要があるかの1行説明

**Current behavior:**
現在の動作を記述します。バグの場合は不具合のある動作を記載します。
改善要望の場合は、新機能の前提となる現状を記載します。

**Desired behavior:**
エージェントの作業完了後に期待される動作を記述します。
エッジケースやエラー条件について具体的に記載してください。

**Key interfaces:**
- `TypeName` — 変更が必要な内容とその理由
- `functionName()` の戻り値の型 — 現在の戻り値とあるべき戻り値
- 設定の構造 — 新たに必要となる設定オプション

**Acceptance criteria:**
- [ ] 具体的でテスト可能な条件1
- [ ] 具体的でテスト可能な条件2
- [ ] 具体的でテスト可能な条件3

**Out of scope:**
- このIssueで変更または対応すべきではない事項
- 関連するように見えて実は別箇所の隣接機能
```

## 例

### 適切なエージェント向け指示書の例（バグ）

```markdown
## Agent Brief

**Category:** bug
**Summary:** スキル説明文の切り詰め処理が単語の途中で切れてしまい、不正な出力が生成される

**Current behavior:**
スキルの説明文が1024文字を超えると、単語の境界を無視して正確に1024文字の地点で切り詰められます。
これにより、単語の途中で終わる説明文が生成されます（例: "Use when the user wants to confi"）。

**Desired behavior:**
切り詰め処理は、1024文字以内の最後の単語境界で行われ、切り詰めを示す "..." を末尾に付加する必要があります。

**Key interfaces:**
- `SkillMetadata` 型の `description` フィールド — 型自体の変更は不要ですが、
  そこに値を設定する検証・処理ロジックで単語境界を考慮する必要があります
- SKILL.md のフロントマターを読み込んで説明文を抽出する各関数

**Acceptance criteria:**
- [ ] 1024文字以下の説明文は変更されない
- [ ] 1024文字を超える説明文は、1024文字以内の最後の単語境界で切り詰められる
- [ ] 切り詰められた説明文の末尾には "..." が付加される
- [ ] "..." を含む合計文字数が1024文字を超えない

**Out of scope:**
- 1024文字の制限自体を変更すること
- 複数行の説明文への対応
```

### 適切なエージェント向け指示書の例（改善要望）

```markdown
## Agent Brief

**Category:** enhancement
**Summary:** 却下された機能リクエストを追跡するための `.out-of-scope/` ディレクトリ対応を追加する

**Current behavior:**
機能リクエストが却下された場合、Issueは `wontfix` ラベルとコメントを付けてクローズされます。
決定内容や判断理由の永続的な記録は残りません。
将来同様のリクエストがあった場合、メンテナーは過去の議論を思い出すか検索する必要があります。

**Desired behavior:**
却下された機能リクエストは `.out-of-scope/<concept>.md` ファイルに記録し、
決定内容、判断理由、その機能を求めたすべてのIssueへのリンクを保持する必要があります。
新しいIssueをトリアージする際、これらのファイルと照合して一致するものを確認する必要があります。

**Key interfaces:**
- `.out-of-scope/` 内のマークダウンファイル形式 — 各ファイルには `# Concept Name` 見出し、
  `**Decision:**` 行、`**Reason:**` 行、およびIssueへのリンクを含む `**Prior requests:**` リストが必要です
- トリアージワークフローは、初期段階で `.out-of-scope/*.md` ファイルをすべて読み込み、
  概念の類似性によって受信したIssueと照合する必要があります

**Acceptance criteria:**
- [ ] 機能を wontfix としてクローズすると、`.out-of-scope/` 内にファイルが作成または更新される
- [ ] ファイルに決定内容、判断理由、クローズされたIssueへのリンクが含まれる
- [ ] 一致する `.out-of-scope/` ファイルがすでに存在する場合、重複作成せずその "Prior requests" リストに新しいIssueが追記される
- [ ] トリアージ中に既存の `.out-of-scope/` ファイルが確認され、新しいIssueが過去の却下内容と一致する場合に提示される

**Out of scope:**
- 自動照合（人間が一致を確認する）
- 過去に却下された機能の再オープン
- バグ報告（改善要望の却下のみが `.out-of-scope/` の対象）
```

### 適切なエージェント向け指示書の例（PR）

PRの場合、「現在の動作」には差分の状態を記述し、指示書ではゼロから構築するのではなく、エージェントに差分の仕上げや修正を求めます。

```markdown
## Agent Brief

**Category:** enhancement
**Summary:** コントリビューターによる `triage list` の `--json` 出力フラグを仕上げる

**Current behavior:**
このPRでは、Issue一覧をJSONにシリアライズする `--json` フラグが追加されています。
正常系は動作しており、差分もプロジェクトのコマンド構造に合致しています。
残る課題は2点です：エラーが依然としてJSONではなくプレーンテキストで出力される点と、
新しいフラグに対するテストカバレッジがない点です。

**Desired behavior:**
`--json` を指定した場合、エラーを含めたすべての出力が標準出力に整形されたJSONとして出力され、
コマンドの終了コードは変更されません。
フラグが指定されていない場合、既存の人間向けテキスト出力は一切変更されません。

**Key interfaces:**
- コマンドのエラー処理パスは、プレーンテキストのエラーの代わりに `--json` のもとで
  `{ "error": string }` を出力する必要があります
- PRで既に追加されているシリアライザーを再利用し、重複して別のものを導入しないでください

**Acceptance criteria:**
- [ ] `triage list --json` が成功時・エラー時の両方で有効なJSONを出力する
- [ ] 終了コードがJSONを指定しないコマンドと一致する
- [ ] `--json` の成功出力と1件のエラーケースをテストで網羅する
- [ ] デフォルト（JSONなし）の出力がバイト単位で完全に不変である

**Out of scope:**
- 他のコマンドへの `--json` の追加
- PRですでに定義されている成功時のJSONレスポンス構造の変更
```

### 不適切なエージェント向け指示書の例

```markdown
## Agent Brief

**Summary:** トリアージのバグを修正する

**What to do:**
トリアージの処理が壊れている。メインファイルを見て修正してください。
150行目付近の関数に問題があります。

**Files to change:**
- src/triage/handler.ts (line 150)
- src/types.ts (line 42)
```

この例が不適切な理由：
- カテゴリがない
- 説明が曖昧（「トリアージの処理が壊れている」）
- 陳腐化しやすいファイルパスや行番号を参照している
- 受け入れ条件がない
- スコープの境界が示されていない
- 現在の動作とあるべき動作の比較が記述されていない
