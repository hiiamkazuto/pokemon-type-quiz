# ADRのフォーマット

ADRは `docs/adr/` に配置し、`0001-slug.md`、`0002-slug.md` のように連番を使用します。

`docs/adr/` ディレクトリは最初のADRが必要になった時点で作成してください。

## テンプレート

```md
# {決定事項の簡潔なタイトル}

{1〜3文: どのような背景があり、何を決定し、なぜそうしたのか。}
```

これだけです。ADRは1段落で構いません。価値があるのは、決定が下された事実とその理由を記録することであり、決められた項目を形式的に埋めることではありません。

## 任意のセクション

真の価値をもたらす場合にのみ含めてください。ほとんどのADRには不要です。

- **ステータス**（フロントマター形式: `proposed | accepted | deprecated | superseded by ADR-NNNN`）— 決定を見直す際に有用
- **検討した選択肢** — 却下した代替案を記録しておく価値がある場合のみ
- **影響と結果** — 自明ではない下流への影響を明記する必要がある場合のみ

## 採番

`docs/adr/` をスキャンして既存の最大番号を確認し、それに1を加えます。

## ADRの作成を提案する基準

以下の3つがすべて満たされている必要があります：

1. **後戻りが困難** — 後から方針を変更するコストが大きい
2. **文脈を知らないと不自然に見える** — 将来コードを読む人が「なぜこのような実装にしたのか？」と疑問に思う
3. **実質的なトレードオフの結果である** — 現実的な代替案が存在し、明確な理由があってそのうちの1つを選択した

方針変更が容易な決定であれば記録は不要です（後から変えればよいため）。不自然でない自明な決定であれば、誰も理由を疑いません。現実的な代替案がなかった場合は「当たり前のことをした」以上の記録する価値がありません。

### 対象となる決定の例

- **アーキテクチャの基本構造** — 「モノレポを採用する」「書き込みモデルはイベントソーシング、読み込みモデルはPostgresへ投影する」
- **コンテキスト間の連携パターン** — 「注文と請求は同期的なHTTPではなくドメインイベントを介して通信する」
- **ロックインを伴う技術選定** — データベース、メッセージバス、認証プロバイダ、デプロイ先など。すべてのライブラリではなく、差し替えに数ヶ月を要するものが該当します。
- **境界とスコープに関する決定** — 「顧客データは顧客コンテキストが所有し、他のコンテキストはID参照のみとする」。明確な「やらないこと」の定義は、「やること」の決定と同等に価値があります。
- **常識的な道筋からの意図的な逸脱** — 「〜という理由により、ORMではなく手動SQLを使用する」。合理的な読者なら逆を想定するような事柄。意図的な設計を将来別のエンジニアが「修正」してしまうのを防ぎます。
- **コード上からは見えない制約** — 「コンプライアンス要件によりAWSは使用できない」「提携先APIの契約上、応答時間を200ms未満にする必要がある」
- **却下理由が自明でない代替案** — GraphQLを検討した上で細かな理由からRESTを採用した場合、それを記録しておきます。そうしないと半年後に別の誰かが再びGraphQLを提案することになります。
