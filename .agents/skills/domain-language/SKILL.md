# ドメイン言語

設計を進めながら、プロジェクトのドメインモデルを能動的に構築し洗練させます。これは能動的な実践です。用語に疑問を投げかけ、エッジケースのシナリオを考案し、用語集や決定事項が明確になった瞬間に書き留めます。単に語彙を確認するために `GLOSSARY.md` を読む行為はこのスキルではありません（それはどのスキルでも行える日常的な参照に過ぎません）。このスキルは、モデルを単に利用するだけでなく変更を加えるためのものです。

## ファイル構造

ほとんどのリポジトリは単一コンテキストです：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `GLOSSARY-MAP.md` が存在する場合、そのリポジトリには複数のコンテキストがあります。マップはそれぞれの配置場所を示します：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← システム全体の決定事項
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← コンテキスト固有の決定事項
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

ファイルは必要になるまで作成しないでください。書き込むべき内容が生じたときにのみ作成します。`GLOSSARY.md` が存在しない場合は最初の用語が確定した時点で作成し、`docs/adr/` が存在しない場合は最初のADRが必要になった時点で作成します。

## セッション中の指針

### 用語集と照らし合わせて指摘する

ユーザーが `GLOSSARY.md` の既存の定義と矛盾する用語を使った場合は、直ちに指摘してください。「用語集では『キャンセル』をXと定義していますが、Yの意味で使われているように見えます。どちらが正しいですか？」

### 曖昧な言葉を研ぎ澄ます

ユーザーが曖昧な用語や複数の意味を持つ用語を使った場合は、正確で統一的な用語を提案してください。「『アカウント』とおっしゃっていますが、顧客とユーザーのどちらを指していますか？これらは別の概念です。」

### 具体的なシナリオを検討する

ドメイン間の関係について議論する際は、具体的なシナリオを用いて検証します。エッジケースを掘り下げ、概念同士の境界線を厳密に定義させるようなシナリオを考案してください。

### コードと照合する

ユーザーが動作仕様を説明した際、実際のコードと一致しているか確認してください。矛盾が見つかった場合は提示します：「コードでは注文全体をキャンセルするようになっていますが、先ほど一部キャンセルが可能とおっしゃいました。どちらが正しいですか？」

### GLOSSARY.md をその場で更新する

用語が確定したら、その場で `GLOSSARY.md` を更新してください。後でまとめて行おうとせず、確定した都度記録します。[GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md) に記載されているフォーマットを使用してください。

`GLOSSARY.md` には実装の詳細を一切含めてはいけません。`GLOSSARY.md` を仕様書やメモ帳、実装上の決定事項の保管場所として扱わないでください。あくまで用語集に徹してください。

### ADRの作成提案は慎重に行う

以下の3つの条件がすべて満たされている場合にのみ、ADRの作成を提案してください：

1. **後戻りが困難** — 後から方針を変更するコストが大きい
2. **文脈を知らないと不自然に見える** — 将来コードを読む人が「なぜこのような実装にしたのか？」と疑問に思う
3. **実質的なトレードオフの結果である** — 現実的な代替案が存在し、明確な理由があってそのうちの1つを選択した

このうち1つでも欠けている場合はADRを作成しないでください。[ADR-FORMAT.md](./ADR-FORMAT.md) のフォーマットを使用してください。
