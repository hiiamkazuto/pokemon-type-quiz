# GLOSSARY.md のフォーマット

## 構造

```md
# {コンテキスト名}

{このコンテキストが何であり、なぜ存在するのかについての1〜2文の説明。}

## 用語

**Order**:
{この用語に関する1〜2文の説明}
_Avoid_: 購入、取引

**Invoice**:
納品後にお客様へ送付される請求書。
_Avoid_: 勘定書、支払いリクエスト

**Customer**:
注文を行う個人または組織。
_Avoid_: クライアント、バイヤー、アカウント
```

## ルール

- **確固たる方針を持つ** — 同じ概念に対して複数の単語が存在する場合は最も適切なものを1つ選び、それ以外を `_Avoid_` に記載します。
- **定義は簡潔に保つ** — 最大でも1〜2文にします。何をするかではなく、それが「何であるか」を定義してください。
- **このプロジェクトのコンテキスト固有の用語のみを含める** — 一般的なプログラミング概念（タイムアウト、エラー型、ユーティリティパターンなど）は、プロジェクトで多用されていても記載しません。用語を追加する前に「これはこのコンテキスト固有の概念か、それとも一般的なプログラミング概念か？」と自問してください。前者のみが該当します。
- **まとまりがある場合は小見出しでグループ化する** — 自然なグループが生じる場合は小見出しで整理します。すべての用語が単一のまとまった領域に属している場合は、フラットな一覧で構いません。

## 単一コンテキストとマルチコンテキストのリポジトリ

**単一コンテキスト（大半のリポジトリ）：** リポジトリ直下に1つの `GLOSSARY.md` を配置します。

**マルチコンテキスト：** リポジトリ直下の `GLOSSARY-MAP.md` に各コンテキストの一覧、配置場所、コンテキスト間の関係を記載します：

```md
# Glossary Map

## Contexts

- [Ordering](./src/ordering/GLOSSARY.md) — 顧客の注文を受注・追跡する
- [Billing](./src/billing/GLOSSARY.md) — 請求書を発行し決済を処理する
- [Fulfillment](./src/fulfillment/GLOSSARY.md) — 倉庫でのピッキングと出荷を管理する

## Relationships

- **Ordering → Fulfillment**: Ordering は `OrderPlaced` イベントを発行し、Fulfillment はそれを受信してピッキングを開始する
- **Fulfillment → Billing**: Fulfillment は `ShipmentDispatched` イベントを発行し、Billing はそれを受信して請求書を発行する
- **Ordering ↔ Billing**: `CustomerId` と `Money` の共有型
```

本スキルは以下の基準で適用すべき構造を判断します：

- `GLOSSARY-MAP.md` が存在する場合はそれを読み込んでコンテキストを特定する
- ルートの `GLOSSARY.md` のみがある場合は単一コンテキスト
- どちらも存在しない場合は、最初の用語が確定した時点でルートに `GLOSSARY.md` を作成する

複数のコンテキストが存在する場合は、現在のトピックがどのコンテキストに関連しているかを判断します。不明な場合はユーザーに確認してください。
