エージェントが利用するあらゆるドキュメント（スキル、`AGENTS.md`、`CLAUDE.md`、ポインタ経由で参照されるドキュメントなど）を作成するためのリファレンスです。形式は異なっても書き方の本質は変わりません。毎回同じ出力を生成するのではなく、エージェントが実行のたびに同じプロセスを踏むようにするための共通の制御手段が存在します。

作成するドキュメントがスキルである場合は、フロントマター、呼び出し方法の選択、ルータースキルについて [`SKILL-MECHANICS.md`](SKILL-MECHANICS.md) を参照してください。

## コンテキストポインタ

**コンテキストポインタ**とは、エージェントのコンテキスト内に保持され、コンテキスト外にある資料の名前と、そこにアクセスするための条件を定義した参照のことです。スキルの説明文はその一例であり、`AGENTS.md` に記載されたドキュメントへの参照行も同じ性質を持ちます。エージェントがその資料に到達するかどうか、そしてどれだけ確実に到達するかを左右するのは、参照先のファイルではなくポインタの文言です。文言が曖昧なポインタの背後にある必須資料は、動作のばらつきを引き起こします。まずはポインタの文言を研ぎ澄まし、それでも解決しない場合にのみ資料を直接インライン化してください。

ポインタには2つの役割があります。その資料が何であるかを明示することと、そこにアクセスする契機となる**分岐**（ドキュメントが扱う個別のケース。これによって実行ごとに異なる経路を辿る）を列挙することです。常時読み込まれるポインタの1語1語はすべてのターンでコストを消費するため、本文以上に徹底的な削ぎ落としが必要です：

- **先頭の単語を重視する** — ポインタは先頭部分でトリガーとしての役割を果たします。
- **1つの分岐につき1つのトリガー** — 同一の分岐を表す類義語の羅列は、1つの分岐を2回書いているのと同じです。それらをまとめ、真に異なる分岐のみを残してください。
- **本文ですでに示されている識別情報は削る** — 本文を読めばわかるメタ情報をポインタに重複して含めないでください。

## 2つの負荷

追加するすべてのドキュメントやポインタは、以下の2つの予算のいずれかを消費します：

- **コンテキスト負荷** — 常時読み込まれる資料がエージェントのコンテキストウィンドウに与えるコスト。`AGENTS.md` の行やスキルの説明文など、毎ターンコンテキストに残り続け、発動するかどうかにかかわらずトークンと注意力を消費します。
- **認知的負荷** — 人間側にかかるコスト。どのようなドキュメントが存在し、いつどれを参照すべきかという把握コストです。人間自身がインデックスとなります。これは最小化すべきコストではなく、人間の主体性を発揮するための代償です。人間の判断が重要な部分には惜しみなく使い、そうでない部分は排除してください。

ポインタを通じてのみ読み込まれる資料は、ポインタ自身の1行分のコストと引き換えにコンテキスト負荷を回避できます。ポインタを一切持たない資料は、完全に認知的負荷のみに依存します。

## 情報階層

ドキュメントは、**手順**（エージェントが実行する一連のアクション）と**リファレンス**（必要に応じて参照される定義、ルール、事実）という2種類の内容から構成されます。これらは自由に組み合わせることができます（すべて手順のレシピ形式、すべてリファレンスの規約集形式、あるいは両方の混合）。核となる判断は、エージェントがその資料をどれほど即座に必要とするかに基づいた階層構造である**情報階層**のどこに各要素を配置するかです：

1. **ファイル内の手順** — 最優先の階層：エージェントが順番に実行する内容。
2. **ファイル内のリファレンス** — 必要に応じて参照される情報。同列でフラットなルール一覧（レビューの全ルールが1つの階層に並ぶなど）となることも多く、これはアンチパターンではなく適切な配置です。
3. **開示リファレンス** — 別のファイルに切り出され、コンテキストポインタ経由で参照され、ポインタが発動したときだけ読み込まれる情報。同一フォルダ内の別ファイルから、あらゆるドキュメントから参照できる外部の参照資料までを含みます。

下位階層へ押し出す情報が少なすぎるとトップレベルが肥大化し、押し出しすぎるとエージェントが真に必要とする情報が隠れてしまいます。このバランスをどう取るかが設計のすべてです。

**段階的開示**とは、メインファイルからポインタの背後へと情報を下位階層へ移し、トップレベルの可読性を保つ手法です。これは単なるトークン数の最適化ではなく、情報階層を守るための手段です。段階的開示の最も明確な判断基準は「分岐」です。すべての分岐で必要とされる情報はインラインで記述し、特定の分岐でのみ必要な情報はポインタの背後へ移します。手順を含むドキュメントにおいて、開示すべきリファレンスがファイル内に居座っていると手順が埋もれてしまい、手順が遵守されるかどうかが運任せになってしまいます。これは単なる読みやすさの問題ではなく、動作のばらつきを左右する要因となります。

**コロケーション**は、ファイル内における配置の原則です。情報階層が「どれだけ深い階層に置くか」を決めるのに対し、コロケーションはその階層の中で「何と何を隣り合わせに置くか」を決めます。ある概念の定義、ルール、注意点は分散させず1つの見出しの下にまとめ、一部を読めば関連情報も自然と視界に入るようにします。その判断基準は、「エージェントのために書かれたドキュメントとして読めるか」です。まとまっているドキュメントはそのように読めますが、散らばっているドキュメントはそう読めません。（重複とは異なります。重複は1つの意味が2箇所以上に現れることですが、散乱は1つの意味が細切れになって複数箇所に分散することです。）

**肥大化**は、ここでの典型的な失敗パターンです。すべての行が必要かつ一意であっても、ドキュメントが単に長すぎる状態を指します。行数が多すぎると注意力が希薄になり、余分な行が増えるほど内容の適切さを保つ保守コストが上がります。その解決策が情報階層です。リファレンスはポインタの背後に開示し、分岐や手順ごとに分割して、各パスが必要な情報だけを運ぶようにしてください。

## 手順と完了基準

すべての手順は、作業の完了をエージェントに知らせる条件である**完了基準**で終わる必要があります。以下の2つの性質が、これを強力な制御手段にします：

- **明確さ** — エージェントは完了と未完了を判別できるか？曖昧な境界（「理解に達した」など）は、真に完了する前に手順を終わらせて完了した気になってしまう**時期尚早な完了**を招きます。先に見えている残りの手順（**完了後の後続手順**）が先を急がせる引力となり、完了基準の明確さがそれに抗う抵抗力となります。以下の順序で対策してください。**まずは境界を研ぎ澄ますこと**（局所的で低コスト）。境界をこれ以上削れず、かつ先急ぎが観察される場合にのみ、手順の連続を分割して後続の手順を視界から隠してください。なお、後続手順を隠す手法は、真のコンテキスト境界（タスクの引き渡しやサブエージェントの起動）を挟む場合のみ有効です。インラインの関数呼び出しでは後続手順がコンテキストに残ったままとなり、何も隠せません。
- **要求水準** — どれだけの作業量を要求しているか。「変更されたすべてのモデルを網羅していること」という記述は徹底的な作業を強制しますが、「変更リストを作成すること」では不十分です。要求水準は**地道な調査**を促進します。これは独立した手順として書かれるのではなく、文言の中に潜在する掘り下げ作業です。また、これは手順だけに限定されません。「すべてのルールを適用すること」という指定は、フラットなリファレンス群を縛り、「すべての手順を完了すること」が手順の連続を縛るのと同様に機能します。これにより、すべてがリファレンスで構成されたドキュメントであっても網羅性を担保できます。

最も強力な完了基準は、客観的に検証可能であり、かつ網羅的なものです。

## 分割の基準

1つのドキュメントを2つに分割すると、2つの負荷のいずれかを消費します。そのため、分割による価値が十分に見合う場合にのみ分割してください：

- **手順による分割** — 後続の手順が存在することで、目の前の手順をエージェントが雑に急いでしまうような箇所で一連の手順を分割します。後続の手順を隠すことで、現在のタスクに対する地道な調査を促進できます。逆の操作（統合）には注意してください。手順を統合すると、各ステップの後続手順が露出し、時期尚早な完了を誘発します。
- **呼び出し方法による分割** — スキル特有の基準です。[`SKILL-MECHANICS.md`](SKILL-MECHANICS.md) を参照してください。

## 牽引語

**牽引語**とは、モデルの事前学習の中にすでに存在し、エージェントがドキュメントを実行する際に思考の軸として利用できる簡潔な概念のことです（教訓、深い霧、曳光弾など）。文ではなく1つのトークンとして繰り返し用いることで、分散された定義を集約し、モデルがすでに保持している知識を活用して、最小限のトークンで特定の振る舞い全体を定着させます。独自の造語を定義して使うことも可能ですが、造語には事前学習の知識が結びついていません。既存の単語が無料で提供してくれる知識を、造語では定義のためのトークンを支払って教え込む必要があります。まずは既存の単語を活用してください。

牽引語は2つの場面で機能します。本文においては**実行**を制御します。その単語が現れるたびにエージェントは同じ振る舞いを呼び起こし、フラットなリファレンスの中では注目すべき対象の分類に注意を集中させます。ポインタにおいては**呼び出し**を制御します。プロンプト、ドキュメント、コードベースの間で同じ単語が使われていると、エージェントはその共通の言葉を資料と結びつけ、より確実にその資料にアクセスできるようになります。

牽引語を使ってリファクタリングできる機会を常に探してください。複数箇所で長々と説明されている事柄や、1つのアイデアを伝えるために1文を費やしているポインタは、いずれも単一のトークンへ凝縮できる兆候です：

- 「高速で、決定論的で、オーバーヘッドが少ない」 → *タイト*（タイトなループ）
- 「信頼できるループ」 → *レッド* — 曖昧な判定が、観察可能な2値の状態（バグに対してテストループがレッドになるか否か）に変わります。

トークン数が減るだけでなく、エージェントが思考を引っ掛けるフックがより鋭くなるという二重のメリットがあります。あらゆるドキュメントには牽引語によって簡略化できる重複表現が含まれていると想定し、それを見つけ出してください。

この手法と隣り合わせにある失敗パターンが**否定表現**です。禁止事項によって行動を制御しようとすると、禁じられた振る舞いがコンテキストに引き込まれ、かえって活性化してしまいます。「白い象のことを考えるな」と言われると象のことしか考えられなくなるように、強い概念に対して否定は弱い修飾語に過ぎず、禁止事項があたかも「それを実行せよ」という指示のように解釈されてしまいます。**肯定的な表現**で指示を構成し、目的とする振る舞い（「1行のコメントを書く」など）を提示することで、禁止すべき振る舞いそのものに言及しないようにしてください。肯定的な表現に言い換えられない絶対的なガードレールとしてのみ禁止表現は価値を持ちます。その場合でも、何を行うべきかに注意が向くよう、肯定的な目標とセットで記述してください。

## 削ぎ落とし

- すべての意味を**唯一の信頼できる情報源**に集約してください。変更が必要になった際、1箇所の修正で済むようにします。**重複**（同じ意味が複数の場所に存在すること）は、保守コストとトークンを浪費し、情報階層におけるその意味の重要度を実態以上に誇大化させてしまいます。（これは牽引語の意図的なトークンの繰り返しとは異なり、無意味な内容の重複です。）
- **環境そのもの**も信頼できる情報源です。`package.json` のスクリプト、設定ファイル、ディレクトリ構造、`--help` の出力などがこれに該当します。それらをドキュメントに書き写したものは単なる**キャッシュ**に過ぎず、確認に多大なコストがかかる場合にのみ記載する価値があります。エージェントが見ればすぐにわかる情報（不文律の規約、選択の背後にある理由、どの設定にも書かれていない落とし穴など）のみをキャッシュしてください。ファイル1つ、コマンド1つで確認できる事項は環境に任せ、情報が古くならないようにします。
- すべての行について**関連性**を検証してください。その行は、ドキュメントが果たす役割に今でも直結しているでしょうか？タスクに一切寄与しない記述（単なる補足説明や、本来開示すべき分岐など）や、振る舞いや環境の変化に伴って古くなった記述は関連性を失います。短いドキュメントほど関連性を維持しやすくなります。削ぎ落としを怠ると、追加は安全だが削除はリスクだと感じられ、結果として古い記述が**沈殿物**のように堆積していきます。やがて何が有効な記述なのかを掘り起こすために余計な労力が必要になってしまいます。
- 文単位で**無意味な指示**を排除してください。モデルがデフォルトで従う指示をわざわざ記述することは、何も言っていないのに負荷を支払っている状態です。そのテスト基準（デフォルトの振る舞いを変えているか？）は、読者ではなくモデルを基準に判断します。無意味な指示かどうかで意見が分かれるのはデフォルトの挙動に対する認識が異なるためであり、議論ではなくドキュメントを実際に実行して検証すべきです。文が不要と判断された場合は、言葉を削るのではなく文全体を削除してください。この基準は牽引語の評価にも適用されます。デフォルトの挙動を打ち破るには弱すぎる単語（エージェントがすでにそこそこ徹底しているときの「徹底的に行え」など）は無意味であり、その解決策は別の手法を試すことではなく、より強力な単語（「容赦なく」など）に変えることです。
