# バグ診断

難解なバグに対処するための規律あるアプローチです。明確な正当化理由がある場合を除き、各フェーズを順番通りに進めてください。

コードベースを探索する際は、`GLOSSARY.md`（存在する場合）を読み込んで関連モジュールの正確なメンタルモデルを把握し、触れる領域に関連するADRを確認してください。

## リダクト

本スキルでは、コマンド、実行結果、キャプチャした成果物を提示します。**必ず最初にすべての機密情報をリダクトしてください**。該当箇所は `<REDACTED>` に置き換えます。認証情報が表示内容ではなく環境内に保持されるよう、環境変数を活用したループを構築してください。キャプチャしたデータに認証ヘッダーが含まれる場合は、診断の手がかりとなる行のみを引用してください。

リダクト後の出力だけでは診断に不足する場合、その旨を明示してユーザーに判断を仰いでください。

## フェーズ1 — フィードバックループの構築

**このフェーズこそが本スキルの真髄です。** これ以降のフェーズはすべて機械的な作業に過ぎません。バグに対する**タイト**な合否判定シグナル（*その*バグに対して確実に**レッド**になるシグナル）が手に入れば、原因は必ず特定できます。二分探索（バイセクト）、仮説検証、計測ログはすべてこのシグナルを利用するだけです。ループがなければ、どれだけコードを眺めても解決には至りません。

ここに並外れた労力を注ぎ込んでください。**徹底的かつ創造的に取り組み、妥協せず構築してください。**

### ループ構築の手段（概ねこの順序で試す）

1. **失敗するテスト** — 単体テスト、結合テスト、E2Eテストなど、バグに到達する任意のシームに配置。
2. **Curl / HTTP スクリプト** — 稼働中の開発サーバーに対して実行。
3. **CLIコマンドの実行** — フィクスチャ入力を与え、正常時のスナップショットと標準出力を差分比較。
4. **ヘッドレスブラウザスクリプト**（Playwright / Puppeteer） — UIを操作し、DOM、コンソール、ネットワーク出力を検証。
5. **キャプチャしたトレースの再生** — 実際のネットワークリクエスト、ペイロード、イベントログをディスクに保存し、対象のコードパス単体で再現実行。
6. **使い捨てハーネス** — 単一の関数呼び出しでバグのコードパスを実行する、システムの最小限のサブセット（1つのサービスとモックされた依存関係）を立ち上げる。
7. **プロパティテスト / ファジングループ** — 「時々不正な出力になる」バグの場合、1000回のランダム入力を実行して失敗パターンを探索。
8. **二分探索ハーネス** — 2つの既知の状態（コミット、データセット、バージョン）の間でバグが発生した場合、「状態Xで起動し、検証し、繰り返す」処理を自動化して `git bisect run` を実行。
9. **差分比較ループ** — 旧バージョンと新バージョン（または2つの異なる設定）に同じ入力を流し、出力を差分比較。
10. **HITL Bashスクリプト** — 最終手段。人間によるクリック操作が不可欠な場合は、`scripts/hitl-loop.template.sh` を使って人間側をナビゲートし、ループの構造を維持。収集した結果をエージェントにフィードバック。

適切なフィードバックループが完成した時点で、バグの90%は解決したも同然です。

### ループのタイト化

構築したループを1つの成果物（プロダクト）として扱ってください。ループを作成できたら、さらに**タイト**に磨き上げます：

- さらに高速化できるか？（セットアップのキャッシュ、無関係な初期化のスキップ、テスト範囲の絞り込み）
- シグナルをより先鋭化できるか？（「クラッシュしなかった」ではなく、具体的な障害の症状を検証する）
- より決定論的にできるか？（日時の固定、乱数シードの固定、ファイルシステムの分離、ネットワークのモック化）

30秒かかる不安定なループは、ループが存在しないのと大差ありません。2秒で確実に再現する決定論的なループこそが、デバッグを加速させる強力な武器となります。

### 非決定論的なバグ

目標は「綺麗な再現」ではなく**再現率の向上**です。トリガーを100回連続実行する、並行化する、負荷をかける、タイミングのウィンドウを狭める、スリープを注入するなど工夫してください。50%の確率で発生するバグはデバッグ可能ですが、1%では不可能です。デバッグ可能な水準に達するまで再現率を引き上げてください。

### ループがどうしても構築できない場合

作業を一旦停止し、その旨を明確に伝えてください。試した内容を一覧化し、ユーザーに以下を求めてください：(a) 再現環境へのアクセス、(b) リダクト済みのキャプチャ資料（HARファイル、ログダンプ、コアダンプ、タイムスタンプ付き画面録画）、または (c) 本番環境への一時的な計測プローブ設置の許可。ループがない状態で仮説の立案へ飛びつく行為は避けてください。

### 完了基準 — レッドになるタイトなループ

フェーズ1の完了条件は、ループが**タイト**であり**レッド化可能**であることです。具体的には、**すでに少なくとも1回は実行した単一のコマンド**（スクリプトのパス、テストの呼び出し、curlなど）を指定でき（リダクトした実行コマンドと出力を提示）、以下の要件を満たしている状態を指します：

- [ ] **レッド化可能** — 実際のバグのコードパスを実行し、**ユーザーが報告した正確な症状**を検証していること。これにより、修正前は確実にレッドになり、修正後はグリーンになること。「エラーなく完走する」ではなく、*この特定のバグを検知できること*。
- [ ] **決定論的** — 毎回の実行で同じ判定結果になること（非決定論的なバグの場合は、前述の通り再現率が十分に引き上げられていること）。
- [ ] **高速** — 分単位ではなく、秒単位で完了すること。
- [ ] **エージェントが実行可能** — 無人で自動実行できること（人間の介入が必要な場合は `scripts/hitl-loop.template.sh` 経由に限定）。

このコマンドが存在する前にコードを読み込んで仮説を立てようとしている自分に気づいたら、**直ちに立ち止まってください。ループなしに仮説へ飛びつくことこそ、本スキルが防ぐべき最大の失敗です。** レッド化可能なコマンドが存在しない限り、フェーズ2へ進んではいけません。

## フェーズ2 — 再現と最小化

ループを実行します。レッドになること（バグが発生すること）を確認してください。

以下を確認します：

- [ ] ループで発生した障害が、**ユーザーが説明した症状そのもの**であること（たまたま近くで発生した別の障害ではないこと。対象のバグを取り違えると修正も誤ったものになります）。
- [ ] 複数回の実行にわたって再現すること（非決定論的なバグの場合は、デバッグに十分な頻度で再現すること）。
- [ ] 後続のフェーズで修正が確実に機能したかを検証できるよう、正確な症状（エラーメッセージ、不正な出力、低速な実行時間）を記録していること。

### 最小化

レッドを確認したら、**レッド状態を維持できる最小のシナリオ**へと再現条件を削ぎ落とします。入力データ、呼び出し元、設定、データ件数、手順を**1つずつ**削り、削るたびにループを再実行します。障害の発生に真に必要な要素（荷重支持要素）だけを残してください。

最小化を行う理由：最小の再現シナリオを作ることで、フェーズ3の仮説空間が狭まり（疑うべき要素が削減される）、フェーズ5におけるクリーンな回帰テストへとそのまま転用できます。

完了条件は、**残っているすべての要素が障害の発生に不可欠である状態**（いずれか1つでも取り除くとループがグリーンになる状態）です。

再現と最小化の両方が完了したことを確認してから次のフェーズへ進んでください。

## フェーズ3 — 仮説の立案

検証を開始する前に、**優先順位をつけた仮説を3〜5個**洗い出してください。1つしか仮説を立てないと、最初に思いついたもっともらしいアイデアに思考が拘束されてしまいます。

各仮説は**反証可能**でなければなりません。その仮説が示す具体的な予測を明記してください。

> 記述形式: 「もし <X> が原因であるならば、<Y を変更する> とバグが解消する / <Z を変更する> と症状が悪化するはずである。」

この予測を明文化できない仮説は、単なる直感に過ぎません。破棄するか、予測可能な形に研ぎ澄ましてください。

**検証に進む前に、優先順位をつけた仮説リストをユーザーに提示してください。** ユーザーが持つドメイン知識によって優先順位が一変したり（「ちょうど #3 に関連する変更をデプロイしたばかりだ」など）、すでに除外済みの仮説を教えてもらえたりすることがよくあります。わずかな確認で大幅な時間を節約できます。返答を長時間待つ必要はありません。ユーザーが不在の場合は自身の優先順位に従って検証を進めてください。

## フェーズ4 — 計測と検証

各検証プローブは、フェーズ3で立てた特定の予測と対応している必要があります。**一度に変更する変数は必ず1つだけにしてください。**

使用するツールの優先順位：

1. **デバッガ / REPLでのインスペクション**（環境がサポートしている場合）。1つのブレークポイントは10行のログ出力に勝ります。
2. 仮説を識別できる境界に絞った**ピンポイントなログ**。
3. 「すべてをログに出力してgrepする」アプローチは避け、仮説の境界に限定してログを配置してください。

**すべてのデバッグ用ログには固有のプレフィックスをタグ付けしてください**（例: `[DEBUG-a4f2]`）。タグを付けておくことで、最終的な後片付けを1回のgrepで完了できます。タグのないログはコードベースに残骸として残りやすく、タグ付きのログは確実に一掃できます。

**パフォーマンスの分岐。** パフォーマンスの低下（リグレッション）に対しては、通常のログ出力はノイズになりがちです。代わりに、ベースラインの測定値（計測ハーネス、`performance.now()`、プロファイラ、クエリ実行計画）を確定させ、そこから二分探索を行ってください。まず測定し、その後に修正します。

## フェーズ5 — 修正と回帰テスト

**修正に着手する前に**回帰テストを作成してください。ただし、テストを配置するための**適切なシーム**が存在する場合に限ります。

適切なシームとは、呼び出し元で実際に発生している**本物のバグパターン**をテストが直接再現できる境界のことです。利用可能なシームが浅すぎる場合（バグの発生に複数の呼び出し元が必要なのに単一の呼び出し元しかテストできない、バグを引き起こした連鎖を再現できない単体テストなど）、そこに回帰テストを置いても誤った安心感を与えるだけです。

**適切なシームが存在しない場合、その事実自体が重要な発見事項です。** その旨を記録してください。コードベースのアーキテクチャが、バグの封じ込めを阻害していることを意味します。この問題を次のフェーズで明示的に提起してください。

適切なシームが存在する場合：

1. 最小化した再現シナリオを、そのシームにおける失敗テストへと変換します。
2. テストが失敗（レッド）することを確認します。
3. 修正を適用します。
4. テストが成功（グリーン）することを確認します。
5. フェーズ1のフィードバックループを、元の（最小化前の）シナリオに対して再実行します。

## フェーズ6 — クリーンアップ

作業完了を宣言する前に、以下をすべて満たしていることを確認してください：

- [ ] 元の再現シナリオでバグが再現しないこと（フェーズ1のループを再実行して確認）
- [ ] 回帰テストが通過すること（適切なシームが存在しなかった場合はその旨が文書化されていること）
- [ ] すべての `[DEBUG-...]` 計測コードが削除されていること（プレフィックスを `grep` して確認）
- [ ] 使い捨てのプロトタイプやハーネスが削除されていること（または明確にマークされたデバッグ用ディレクトリへ退避されていること）
- [ ] 正しかった仮説の内容がコミットメッセージやPRの説明文に記載されていること（将来同じ領域をデバッグする開発者のための教訓とする）
