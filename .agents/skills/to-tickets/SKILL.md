# チケットへの分割

計画、仕様書、または会話内容を、一連の**チケット**（各チケットを**ブロック**している前提チケットを宣言した、全レイヤーを貫く垂直スライスである曳光弾チケット）に分割します。

Issueトラッカーおよびトリアージラベルの体系は事前に提供されている必要があります。まだ提供されていない場合は、ユーザーに `/setup-skills` の実行を案内してください。

## プロセス

### 1. 状況の把握

現在の会話の文脈にある情報をベースに進めます。ユーザーが引数として参照情報（仕様書のパス、Issue番号、URLなど）を渡した場合は、それを取得して本文とコメントの全体を読み込んでください。

### 2. コードベースの探索（任意）

まだコードベースを探索していない場合は探索を行い、コードの現状を把握します。チケットのタイトルと説明にはプロジェクトのドメイン用語集の用語を使用し、触れる領域に関連するADRを尊重してください。

実装を容易にするための事前リファクタリングの機会を探してください。「まず変更を容易にしてから、容易な変更を行う」という原則に従います。

### 3. 垂直スライスのドラフト作成

作業を**曳光弾**チケットに分割します。

<vertical-slice-rules>

- 各スライスは、すべてのレイヤー（スキーマ、API、UI、テスト）を貫く、狭くとも完全な一筋の経路を切り開く必要があります — 特定の1レイヤーを水平に切り分けるのではなく、垂直に切り分けます
- 完了したスライスは、それ単体でデモ可能または検証可能である必要があります
- 各スライスは、まっさらな単一のコンテキストウィンドウに収まるサイズにします
- 事前リファクタリングが必要な場合は最初に行います

</vertical-slice-rules>

各チケットに**依存関係**を設定します — そのチケットを開始する前に完了していなければならない他のチケットを指定します。ブロッカーのないチケットは今すぐ着手できます。

**広範囲に及ぶリファクタリングは垂直スライスの例外です。** **広範囲なリファクタリング**とは、カラム名の変更や共通シンボルの型変更など、機械的な1つの変更でありながら**影響範囲**がコードベース全体に波及するものを指します。1箇所の編集で何千もの呼び出し元が一度に壊れてしまうため、垂直スライス単体でテストを合格の状態にすることができません。これを無理に曳光弾に押し込めようとせず、**展開と縮小**の手順で進めてください。まず「展開」：古い形式の隣に新しい形式を追加し、既存のコードが壊れないようにします。次に、影響範囲に応じた単位（パッケージごと、ディレクトリごとなど）にバッチを分け、呼び出し側を順次移行します。各バッチは「展開」チケットにブロックされた独立したチケットとし、古い形式が残っているためバッチごとにCIのテストが合格の状態を保ちます。最後に「縮小」：すべての呼び出し元の移行が完了した段階で、移行バッチのすべてにブロックされたチケットとして古い形式を削除します。バッチ単体でも合格を維持できない場合は、この順序を維持しつつ各バッチで統合ブランチを共有し、最終的な統合・検証チケットをブロックするようにします（テスト合格の保証はその最終チケットでのみ行います）。

### 4. ユーザーへの確認

提案する分割案を番号付きリストで提示します。各チケットについて以下を示してください：

- **タイトル**：簡潔で内容が伝わる名称
- **依存先**：先に完了していなければならない他のチケット（ある場合）
- **提供する価値**：このチケットによって動作するようになるエンドツーエンドの振る舞い

ユーザーに以下を確認します：

- 粒度は適切か？（粗すぎないか、細かすぎないか）
- 依存関係は正しいか — 各チケットが、真に着手を阻んでいるチケットにのみ依存しているか？
- さらに統合または分割すべきチケットはあるか？

ユーザーが分割案を承認するまで調整を繰り返してください。

### 5. 設定されたトラッカーへのチケットの公開

承認されたチケットを公開します。**どのように**公開するかは `/setup-skills` で設定されたトラッカーによって異なります。チケットの内容自体はどちらでも同じですが、依存関係の表現形式のみが異なります：

- **ローカルファイル** → `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 配下に、依存順（ブロッカーが先）で `01` から採番して1チケット1ファイルとして書き込みます。各ファイルの「Blocked by」行に、依存している番号やタイトルを記載します。後述のチケット用ファイルテンプレートを使用してください（1チケット1ファイルとし、決して1つのファイルにまとめないでください）。
- **本物のIssueトラッカー（GitHub、Linearなど）** → 各チケットの依存関係が実在する識別子を参照できるよう、依存順（ブロッカーが先）で1チケットにつき1つのIssueを公開します。プラットフォームにネイティブの依存関係機能やサブIssue機能がある場合はそれを使用し、ない場合は各チケットの「Blocked by」セクションに対象のIssueを指定します。特に指示がない限り、トリアージラベル `ready-for-agent` を適用してください（構造上、これらのチケットはエージェントが直ちに着手できる状態になっています）。

**フロンティア**（ブロッカーがすべて完了しているチケット）を進めます。純粋に直列な依存関係の場合は、上から下へと進めることを意味します。

親Issueをクローズしたり変更したりしては**いけません**。

<local-ticket-template>

# <NN> — <チケットのタイトル>

**What to build:** ユーザーの視点から見て、このチケットによって動作するようになるエンドツーエンドの振る舞い（レイヤーごとの実装リストではありません）。

**Blocked by:** このチケットの前提となるチケットの番号やタイトル、または「なし — 今すぐ着手可能」。

**Status:** ready-for-agent

- [ ] 受け入れ条件1
- [ ] 受け入れ条件2

</local-ticket-template>
