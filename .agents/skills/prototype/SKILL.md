# プロトタイプ

プロトタイプとは、**ある問いに答えるための使い捨てのコード**です。問いの内容によってプロトタイプの形態が決まります。

## 分岐の選択

ユーザーの指示、周囲のコード、またはユーザーがその場にいれば直接質問することで、どの問いに答えようとしているのかを特定してください：

- **「このロジックや状態モデルは適切か？」** → [LOGIC.md](LOGIC.md)。自由に操作できるボタンとタブ形式のガイド付きウォークスルーを備えた、単一の共有可能なHTMLファイルを作成します。机上では検討しにくいケースを通じてステートマシンを動かし、非エンジニアでも実際に操作できるようにします。
- **「どのような見た目にするべきか？」** → [UI.md](UI.md)。単一のルーティング上で、URL検索パラメータと画面下部のフローティングバーによって切り替え可能な、根本的に異なる複数のUIバリエーションを生成します。

これら2つの分岐はまったく異なる成果物を生み出します。ここを取り違えるとプロトタイプ全体が無駄になります。問いが本質的に曖昧でユーザーに確認できない場合は、周囲のコードにより適合する分岐をデフォルトとし（バックエンドモジュールならロジック、ページやコンポーネントならUI）、その前提をプロトタイプの先頭に明記してください。

## 共通のルール

1. **最初から使い捨てとして扱い、それを明確に示すこと。** プロトタイプのコードは、文脈が明確に伝わるよう実際に使われる場所の近く（対象のモジュールやページの隣）に配置します。ただし、誰が見ても本番コードではなくプロトタイプだとわかるように命名してください。使い捨てのUIルーティングについても、プロジェクト既存のルーティング規約に従い、独自のトップレベル構造を勝手に作成しないでください。
2. **簡単に実行できること。** UIプロトタイプは、プロジェクトのタスクランナーから1つのコマンド（`pnpm <名前>`、`python <パス>`、`bun <パス>` など）で起動できるようにします。ロジックのデモは、ユーザーがダブルクリックするだけの単一HTMLファイルとします。どちらの場合も、起動にあたって余計な思考を必要とさせないでください。
3. **デフォルトではデータを永続化しないこと。** 状態はメモリ上に保持します。永続化はプロトタイプが「検証」する対象であり、依存すべきものではありません。問いが明確にデータベースに関わる場合は、スクラッチ用DBや「PROTOTYPE — 削除可能」と明記したローカルファイルを使用してください。
4. **細部の磨き込みは省くこと。** テストは書かず、プロトタイプが「実行可能」になる最低限を超えるエラーハンドリングは行わず、抽象化も避けてください。目的は迅速に学びを得ることです。
5. **状態を可視化すること。** 各アクションの実行後（ロジック）やバリアントの切り替え時（UI）には、何が変化したかがユーザーに伝わるよう、関連する状態の全体を出力または画面描画してください。
6. **完了時に記録を残すこと。** 検証済みの決定事項を本番コードに取り込み、プロトタイプ自体は**一次資料**として記録します。mainブランチから外れた使い捨てブランチにコミットし、実装Issue上にそのブランチへのポインタを残してください。結論とそれが解決した問いという「回答」も、Issueやコミットに記録します。mainブランチには検証済みの決定事項のみを残してください。
