# ロジックのプロトタイプ

ボタンをクリックすることで誰もが状態モデルを動かせる、単一の自己完結型HTMLファイル（**共有可能なデモ**）を作成します。**ビジネスロジック、状態遷移、またはデータ構造**についての問い、すなわち机上では問題なさそうに見えるものの実際のケースを通してみて初めて違和感に気づくような事柄に対して使用します。

インストール不要の単一ファイルであるため、デザイナー、プロダクトマネージャー、ドメインエキスパートなどの非エンジニアにも渡して、実際にモデルの手触りを体験してもらえます。そのため、コードの言葉ではなく彼らの言葉で表現します。

## 適したケース

- 「このステートマシンが、Xの後にYが発生するエッジケースを適切に処理できるか確信が持てない」
- 「このデータモデルで、〜のようなケースを実際に表現できるだろうか」
- 「APIを実装する前に、どのような構造にすべきか手触りを確かめたい」
- **ボタンを押して状態の変化を観察したい**あらゆるケース

「どのような見た目にするべきか」が問いである場合は分岐が異なります。[UI.md](UI.md) を使用してください。

## プロセス

### 1. 問いの明文化

コードを書く前に、どのような状態モデルとどのような問いについてプロトタイプを作成するのかを書き留めます。デモの冒頭に1段落で記述してください（単なるコメントではなく、画面上に表示される説明文として配置します）。間違った問いに答えるロジックプロトタイプはまったくの無駄になります。ユーザーが今その場で見ているか、後から非同期で確認するかにかかわらず検証できるよう、問いを明確にしてください。

### 2. ロジックを移植可能なモジュールとして分離する

問いに直接答える実際のロジック部分を、後から本番のコードベースにそのまま移植できる小さく純粋なモジュールとして、単一の `<script>` ブロック内に記述します。周囲のHTMLページは使い捨てですが、このモジュール自体は使い捨てではありません。

適切な形態は問いの内容によって異なります：

- **純粋なリデューサー** — `(state, action) => state`。アクションが個別のイベントであり、状態が単一の値である場合に適しています。
- **ステートマシン** — 明示的な状態と遷移。「現時点でどのアクションが正当であるか」自体が問いの一部である場合に適しています。
- **プレーンなデータ型に対する純粋関数群** — 暗黙的な現在の状態が存在せず、データの変換のみを行う場合に適しています。
- **明確なメソッドを持つクラスやモジュール** — ロジック自身が継続的な内部状態を真に保持している場合に適しています。

ページへの繋ぎ込みやすさではなく、問われている内容に最も適した形態を選択してください。DOMや `document` を参照せず、ボタンのイベントハンドラーが内部に侵入しない純粋な状態を保ちます。ページ側からモジュールを呼び出す一方通行とし、逆方向への依存は一切持たせません。これにより、問いが解決した後に、検証済みのリデューサーやステートマシン、関数群を本番モジュールへそのまま移植できるようになります。

### 3. 共有可能なHTMLファイルの構築

フレームワーク、バンドラー、サーバーを一切使用せず、HTML、CSS、JavaScriptのみで構成された単一ファイルを作成します。ダブルクリックするだけで開き、メールなどで配布してもそのまま動作するよう、すべてをインラインで記述します。開くだけで誰もが実行できるようにします。

非エンジニアに向けて記述してください。すべてのラベルはコードではなく**ドメイン言語**を用います。ボタンや状態の表示は、リデューサーではなくビジネス側の用語に合わせます。何が起きているのかを平易な言葉で説明してください。

上から下へ明確な階層構造で配置します：

1. **タイトルと1行説明** — このデモで何を検証できるのか（ステップ1で定めた問い）。
2. **現在の状態** — 関連するすべての状態を、読みやすいパネル形式で表示します（生のJSONダンプではなく、ラベル付きの各項目として表示）。クリックのたびに再描画して変化を可視化します。非エンジニアの理解を助けるため、直前に何が変化したかを明示します。
3. **自由操作ボタン** — 誰もが任意の順序でモデルを操作できるよう、各アクションに対応するボタンを常時利用可能にしておきます。クリックするたびにアクションが実行され、状態が再描画されます。
4. **ガイド付きウォークスルー** — タブごとに1つずつ用意された**シナリオ**のセットです。各タブには、シナリオの平易な説明（どのような状況を設定し、何に注目すべきか）を記載し、その下に対応する**順番に押すべきボタン**を配置します。各ステップは実際のボタンであり、クリックするとそのアクションが実行されて次のステップへ進みます。ウォークスルーを開始すると既知の初期状態にリセットされ、毎回同じようにシナリオが実行されるようにします。

机上では検討しにくいケース（正常系、厄介なエッジケース、本来不正であるべき操作の試行など）を実証できるシナリオを選択してください。

デザインは抑制の効いた美しさに保ちます。整ったタイポグラフィ、十分な余白、単一のアクセントカラーを使用します。状態やボタンの視認性を損なうアニメーションや装飾は避けてください。

### 4. 相手への受け渡し

ファイルを相手に送信するか、相手の目の前で開きます。相手は時間のあるときにウォークスルーや自由操作を進めます。「そんな動作はおかしい」「ここは違う結果になると思っていた」といった反応が得られた瞬間が最も重要です。それこそが**アイデア自体の不具合**であり、プロトタイプを作る本来の目的です。新しいアクションや新しいシナリオの要望が出た場合は追加してください。プロトタイプは進化させていくものです。

### 5. 回答とプロトタイプの記録

プロトタイプが問いに答えを出したら、その回答を記録し、[SKILL](SKILL.md) の説明に従ってプロトタイプ自体を保管します。ロジックの場合の具体的な対応：検証済みのリデューサー、ステートマシン、関数群は本番モジュールへ移植し（決定事項の吸収）、HTMLシェルは一次資料としてプロトタイプを保持する使い捨てブランチにコミットします。自己完結した単一ファイルであるため、そのブランチ上でも簡単に再実行できます。

## アンチパターン

- **テストを追加しないこと。** テストが必要になったプロトタイプは、もはやプロトタイプではありません。
- **本番のデータベースに接続しないこと。** 永続化そのものが検証対象である場合を除き、インメモリの状態を使用してください。
- **汎用化しないこと。** 「後からXにも対応したくなったらどうするか」といった配慮は不要です。プロトタイプは1つの問いに答えるためのものです。
- **ロジックと画面表示を混在させないこと。** 純粋モジュールがDOMや `document`、ボタンハンドラーを参照してしまうと、移植できなくなります。HTMLページは純粋モジュールを包む薄いシェルに留めてください。
- **フレームワーク、バンドラー、サーバーに手を出さないこと。** 相手がダブルクリックするだけの単一ファイルであることが重要です。Reactアプリや開発サーバーを必要とすると「手軽な共有」が損なわれます。
- **HTMLシェルを本番コードに持ち込まないこと。** このページは手動でクリックして確認することに特化しています。残すべき価値があるのは、その背後にあるロジックモジュールです。
