# UIプロトタイプ

単一のルーティング上で、画面下部のフローティングバーから切り替え可能な**根本的に異なる複数のUIバリエーション**を生成します。ユーザーはブラウザ上で各バリアントを切り替え、1つを選び（または各案の良い部分を抽出し）、残りは破棄します。

見た目ではなくロジックや状態に関する問いである場合は分岐が異なります。[LOGIC.md](LOGIC.md) を使用してください。

## 適したケース

- 「このページをどのような見た目にすべきか」
- 「ダッシュボードを確定する前にいくつか選択肢を見てみたい」
- 「設定画面の別のレイアウトを試したい」
- 頭の中にある3つの漠然としたモックアップの比較に丸一日費やしてしまいそうなあらゆる場面

## 2つのサブパターン — サブパターンAを強く推奨

UIプロトタイプは、**アプリの他の部分（本物のヘッダー、サイドバー、データ、情報密度）と隣接している状態**のほうがはるかに判断しやすくなります。孤立した使い捨てルーティングは密室のようなものであり、単体で見るとどのバリアントも良く見えてしまいます。バリアントを配置できる既存ページが存在する場合は、常にサブパターンAを選択してください。プロトタイプを配置できる場所が近くにまったく存在しない場合にのみ、サブパターンBを使用します。

### サブパターンA — 既存ページへの適用（推奨）

対象のルーティングがすでに存在する場合です。各バリアントは、URL検索パラメータ `?variant=` によって切り替えられ、**同一のルーティング上にレンダリング**されます。既存のデータ取得、パラメータ、認証処理はすべて維持し、レンダリング部分のみを差し替えます。これがデフォルトであり、特別な理由がない限りこちらを選択してください。

まだ独立したページがないものの、*自然とその中に配置されるべき要素*（ダッシュボードの新しいセクション、設定画面の新しいカード、既存フロー内の新しいステップなど）のプロトタイプを作成する場合も、サブパターンAに該当します。ホストとなるページ内にバリアントを組み込んでください。

### サブパターンB — 新規ページの作成（最終手段）

完全に新しいトップレベルの画面や、既存のどこにも適切に組み込めないフローなど、プロトタイプを配置できる既存ページが一切存在しない場合にのみ使用します。

プロジェクト既存のルーティング規約に従って**使い捨てルーティング**を作成してください（独自のトップレベル構造を勝手に考案しないでください）。プロトタイプであることが一目でわかるように命名します（パスやファイル名に `prototype` という単語を含めるなど）。同様に `?variant=` パターンを使用します。

サブパターンBに決める前に、「本当に組み込める既存ページがないか？」を再確認してください。中身のない空のルーティングでは、データが入った実際の画面なら見つかるはずの設計上の問題が隠れてしまいます。

どちらのサブパターンでも、画面下部のフローティングバーは共通です。

## プロセス

### 1. 問いの明確化とバリアント数の決定

デフォルトは**3つのバリアント**です。5つを超えると根本的な違いがなくなり単なるノイズになるため、それを上限としてください。

プロトタイプの配置場所やファイル先頭のコメントに、計画を1行で記述します：

> 「既存の `/settings` ルーティング上で、`?variant=` により切り替え可能な設定ページの3つのバリアント。」

これにより、ユーザーがその場に立ち会っているかどうかにかかわらず作業を進められます。

### 2. 根本的に異なるバリアントの生成

各バリアントを作成します。各バリアントにおいて以下を遵守してください：

- そのページの目的と、アクセス可能なデータ
- プロジェクトのコンポーネントライブラリやスタイリング構成（TailwindCSS、shadcn、MUI、プレーンCSSなど）
- `VariantA`、`VariantB`、`VariantC` といった明確なエクスポート用コンポーネント名

バリアントは**構造的に異なっている**必要があります。単に色が違うだけでなく、レイアウト、情報の優先順位、主要な操作手段が異なっていなければなりません。少し手直しした程度のカードグリッドを3つ並べてもUIプロトタイプにはならず、ただの壁紙に過ぎません。2つの案が似すぎてしまった場合は、「カードグリッドは使わない」といった明確な制約を設けて作り直してください。

### 3. スイッチャーによる連携

対象のルーティング上に、単一の切り替えコンポーネントを作成します：

```tsx
// 疑似コード — プロジェクトのフレームワークに合わせて適応
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

サブパターンA（既存ページ）の場合：データ取得処理はすべてスイッチャーの手前に残し、バリアントごとにレンダリングされるサブツリーのみを変更します。

サブパターンB（新規ページ）の場合：`/prototype/<名前>` 配下の使い捨てルーティングに、同様のスイッチャーを組み込みます。

### 4. フローティングスイッチャーの構築

画面下部の中央に配置する小さな固定バーであり、3つの要素で構成されます：

- **左矢印** — 前のバリアントへ循環切り替え。
- **バリアントのラベル** — 現在のバリアントキーを表示し、バリアントに名前が定義されている場合はその名前も併記します（例: `B — サイドバーレイアウト`）。
- **右矢印** — 次のバリアントへ循環切り替え。

振る舞い：

- 矢印をクリックするとURL検索パラメータが更新され（Next.js の `router.replace` や React Router の `navigate` など、フレームワークのルーターを使用）、バリアントのURLを共有可能で、リロードしても維持されるようにします。
- キーボード操作：`←` および `→` の矢印キーでも切り替えを可能にします。`<input>`、`<textarea>`、`[contenteditable]` にフォーカスがある場合はキーイベントを拾わないようにしてください。
- 評価対象のデザインと混同されないよう、画面と明確に区別できる外観にします（高コントラストのカプセル型、控えめなシャドウなど）。
- 本番ビルドでは非表示にします。`process.env.NODE_ENV !== 'production'` などの条件で制御し、プロトタイプが誤ってマージされてもユーザーにバーが表示されないようにします。

どちらのサブパターンでも再利用できるよう、スイッチャーは単一の共通コンポーネントとして作成し、プロジェクト内の共通UI置き場に配置してください。

### 5. 相手への受け渡し

URL（および `?variant=` のキー）を伝えます。相手は都合の良いときに切り替えて確認します。最も有意義なフィードバックは、通常**「BのヘッダーとCのサイドバーを組み合わせたい」**といった意見です。それこそが相手が真に求めているデザインです。

### 6. 回答の記録とクリーンアップ

採用する案が決まったら、どのバリアントをなぜ選んだかという回答を記録し、[SKILL](SKILL.md) の説明に従ってプロトタイプ自体を保管します。選ばれたバリアントを本番コードに取り込み、残りはmainブランチではなく使い捨てブランチに移動します：

- **サブパターンA** — 選ばれたバリアントを既存のページに反映し、不採用となったバリアントとスイッチャーをmainブランチから削除します。
- **サブパターンB** — 選ばれたバリアントを本番のルーティングへ昇格させ、使い捨てルーティングとスイッチャーをmainブランチから削除します。

バリアント一式は一次資料であるため、破棄するのではなく使い捨てブランチに保管します。バリアントのコンポーネントやスイッチャーをmainブランチに残しておくと、すぐに陳腐化して将来コードを読む人を混乱させます。

## アンチパターン

- **色や文言しか違わないバリアントを作ること。** それは単なる微調整であり、プロトタイプではありません。真のバリアントは構造が異なっています。
- **バリアント間でコードを共通化しすぎること。** 共通の `<Header>` は問題ありませんが、共通の `<Layout>` を作ると意味がなくなります。各バリアントは自由にレイアウトを変更できる必要があります。
- **バリアントを本物の更新処理に接続すること。** 読み取り専用のプロトタイプで十分です。更新が必要な場合はスタブに向けてください。目的は「どのような見た目にすべきか」の確認であり、「バックエンドが動作するか」ではありません。
- **プロトタイプのコードをそのまま本番に昇格させること。** バリアントのコードはプロトタイプの制約下（テストなし、最低限のエラーハンドリング）で書かれています。取り込む際は適切に書き直してください。
