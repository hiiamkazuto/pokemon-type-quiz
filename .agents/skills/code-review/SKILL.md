`HEAD` とユーザーが指定した基準点との間の差分に対する2軸レビューです：

- **Standards** — コードはこのリポジトリに文書化されたコーディング規約に準拠しているか？
- **Spec** — コードは元となるIssueや仕様書の内容を忠実に実装しているか？

互いのコンテキストを汚染しないよう、両方の軸は**並行サブエージェント**として実行され、本スキルが双方の結果を集約します。

Issueトラッカーの情報は事前に提供されている必要があります。`docs/agents/issue-tracker.md` が存在しない場合は、ユーザーに `/setup-skills` の実行を案内してください。

## プロセス

### 1. 基準点の確定

ユーザーが指定した基準点（コミットハッシュ、ブランチ名、タグ、`main`、`HEAD~5` など）を採用します。指定がない場合は質問してください。

差分取得コマンドを一度確認します：`git diff <fixed-point>...HEAD`（マージベースとの比較となるよう3つのドットを使用）。また、`git log <fixed-point>..HEAD --oneline` でコミットの一覧も確認します。

先へ進む前に、基準点が解決可能であること（`git rev-parse <fixed-point>`）と、差分が空でないことを確認してください。無効な参照や空の差分は、2つの並行サブエージェントを立ち上げる前にここで検知して失敗させる必要があります。

### 2. 仕様元の特定

元となった仕様を以下の順序で探します：

1. コミットメッセージ内のIssue参照（`#123`、`Closes #45`、GitLabの `!67` など）— `docs/agents/issue-tracker.md` のワークフローに従って取得。
2. ユーザーが引数として渡したパス。
3. `docs/`、`specs/`、または `.scratch/` 配下にある、ブランチ名や機能名と一致する仕様書ファイル。
4. 何も見つからない場合は、仕様書の場所をユーザーに尋ねます。仕様書が存在しないと回答された場合、**Spec** サブエージェントはスキップし、「仕様書がありません」と報告します。

### 3. 基準元の特定

`CODING_STANDARDS.md` や `CONTRIBUTING.md` など、コードの書き方が文書化されているリポジトリ内のファイル。

リポジトリに何が文書化されているかに加え、Standards軸には常に後述の**コードスメルのベースライン**が適用されます。これはリポジトリ側に何の文書もない場合でも適用される、ファウラーのコードスメル（『リファクタリング』第3章）の固定セットです。以下の2つのルールが適用されます：

- **リポジトリの規約を優先する。** 文書化されたリポジトリの規約が常に優先されます。ベースラインがフラグを立てるような内容であっても、リポジトリの規約がそれを認めている場合は指摘を抑制してください。
- **常に判断を伴うヒューリスティックである。** 各コードスメルはラベル付けされたヒューリスティック（機能の横取りの可能性など）であり、絶対的な違反ではありません。また、ツールがすでに自動強制している事項はスキップしてください。

各コードスメルは「何であるか」と「どう修正するか」を示しています。差分と照合してください：

- **不可解な名前** — 何を行い何を持つかが名前からわからない関数、変数、または型。→ 名前を変更します。適切な名前が思い浮かばない場合は、設計が不透明です。
- **重複したコード** — 変更内の複数のハンクやファイルに同じロジックの形状が現れている。→ 共通の処理を抽出し、双方から呼び出します。
- **機能の横取り** — 自身のデータよりも他のオブジェクトのデータに過度にアクセスしているメソッド。→ そのメソッドを、それが依存しているデータ側のオブジェクトへ移動します。
- **データの群れ** — 常に一緒に渡されるいくつかのフィールドやパラメータ（新しい型として切り出されるべきもの）。→ それらを1つの型にまとめ、それを渡します。
- **基本データ型への執着** — 独自の型を持つべきドメイン概念に対して、基本データ型や文字列を代用している。→ その概念に対して専用の小さな型を定義します。
- **繰り返されるswitch文** — 同一の型に対する同じ `switch`/`if` の連続が変更全体で再発している。→ ポリモーフィズムに置き換えるか、双方が共有する1つのマップに置き換えます。
- **変更の分散** — 1つの論理的な変更のために、差分内の多数のファイルに編集が散らばっている。→ 一緒に変更されるものを1つのモジュールに集約します。
- **変更の偏り** — 1つのファイルやモジュールが、互いに無関係な複数の理由で編集されている。→ 各モジュールが1つの理由でのみ変更されるよう分割します。
- **疑わしき一般化** — 仕様に存在しない要求のために、抽象化、パラメータ、またはフックが追加されている。→ 削除します。真の必要性が現れるまでインラインに戻します。
- **メッセージの連鎖** — 呼び出し元が依存すべきではない `a.b().c().d()` のような長い参照の連鎖。→ 最初のオブジェクト上の1つのメソッドの背後に一連の呼び出しを隠蔽します。
- **仲介人** — 処理のほとんどを他へ転送するだけのクラスや関数。→ 削除し、真の対象を直接呼び出します。
- **拒絶された遺産** — 継承元の機能の大部分を無視またはオーバーライドしているサブクラスや実装。→ 継承をやめ、コンポジションを使用します。

### 4. 両方のサブエージェントを並行して起動する

**Standards サブエージェントへの指示** — 以下を含めます：

- 完全な差分取得コマンドとコミット一覧。
- ステップ3で見つかった基準となるファイルの一覧、**およびステップ3のコードスメルのベースラインの全文**（サブエージェントはこれ以外に参照手段がありません）。
- 指示内容：「差分の該当するファイルやハンクごとに以下を報告してください。(a) 文書化された基準に違反しているすべての箇所（基準のファイル名とルールを引用）。(b) 発見したベースラインのコードスメル（名称を挙げ、ハンクを引用）。絶対的な違反と判断事項を明確に区別してください。文書化された規約への違反は絶対的な違反になり得ますが、ベースラインのコードスメルは常に判断を伴うものであり、文書化されたリポジトリの基準がベースラインに優先します。ツールが強制している内容はスキップしてください。400語以内。」

**Spec サブエージェントへの指示** — 以下を含めます：

- 差分取得コマンドとコミット一覧。
- 仕様書のパスまたは取得した内容。
- 指示内容：「以下を報告してください。(a) 仕様書で求められているにもかかわらず欠落している、または不完全な要件。(b) 仕様書で求められていない差分内の振る舞い（スコープの拡大）。(c) 実装されているように見えるが誤っている要件。指摘ごとに仕様書の行を引用してください。400語以内。」

仕様書が存在しない場合は、Specサブエージェントをスキップし、最終レポートにその旨を記載します。

### 5. 結果の集約

2つのレポートを `## Standards` および `## Spec` の見出しの下に、そのまま、または軽く整形して提示します。指摘事項を統合したり優先順位を並べ替えたりしては**いけません**。2つの軸は意図的に分離されています（後述の「なぜ2つの軸なのか」を参照）。

末尾に1行の要約を添えます：軸ごとの総指摘件数、および*各軸における*最も重大な問題（ある場合）。両方の軸をまたいで1つの勝者を決めるような順位付けは行わないでください。そうした並べ替えを防ぐためにこそ軸を分離しています。

## なぜ2つの軸なのか

変更内容は、一方の軸に合格して他方の軸で不合格になることがあります：

- すべての規約に従っているが、誤った機能を実装しているコード → **Standards は合格、Spec は不合格**
- Issueが求めた通りの動作をするが、プロジェクトの規約に違反しているコード → **Spec は合格、Standards は不合格**

これらを分けて報告することで、一方の軸がもう一方の軸の問題を覆い隠してしまうのを防ぎます。
